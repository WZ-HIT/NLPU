# 测试定位研究：PPT 素材包

整理日期：2026-11-03  
用途：组会／中期进展汇报的页面素材、讲稿、表格和答辩要点。  
默认假设：听众是熟悉软件工程但不一定了解本项目的老师／同学；时长 15–20 分钟；主线是“问题—路线—证据—判断—下一步”，不是论文最终答辩。若实际是开题／答辩，删去工程细节，强化问题定义、方法创新和泛化验证计划。

## 0. 一句话主线

> 我们研究“只给开发任务描述和任务前仓库，如何定位需要更新的已有测试方法”；目前已建立可复现的数据与评价协议，系统比较了检索基线和三种 SDD 直接定位，并用测试意图表示把定位成功率从“被预算拖垮”推进到“部分 SDD 有增益”，但尚未证明三种 SDD 全面提升，也尚未完成同环境的因果对照。

建议全篇反复回到三句话：

1. **任务不是“找相关测试”，而是“找需要改的已有测试”。**
2. **分数要同时看完成率、macro 与 micro，不能只看一个均值。**
3. **当前最可靠的结论是“机制可行、部分改善、因果未定”，不是“方法已经全面有效”。**

---

## 1. 建议叙事结构

### 第一幕：问题（2–3 页）

- 开发任务来了，实现 diff 还没有；工程师仍要判断哪些旧测试会受影响。
- 现有检索／覆盖率工具回答的是“相关”或“要重跑”，不是“必须维护”。
- 输出必须落到测试函数／方法，文件级只是中间结果。

### 第二幕：基线与瓶颈（3–4 页）

- 四种方法级检索基线：Jina-code 在 Recall@200 上最高（64.52%），但候选精度只有约 2%。
- 三种 SDD 直接定位：macro recall 32.76%–44.80%，且 35/90 运行失败。
- 结论：光靠“任务文本 → 测试源码”的词法／向量相似度，候选召回有上限；光靠 SDD，运行成本和判断稳定性是瓶颈。

### 第三幕：增强与证据（5–6 页）

- 测试意图表示：把分散在 fixture、mock、断言、调用里的行为整理成可检索卡片。
- 第一版完整证据包：表示太大，90 项中 64 项预算耗尽，指标反而下降。
- 诊断：失败不全是“没找到”，而是把预算花在找目录、修工具、读大段材料上。
- 精简版：材料读取字符降 85.75%，预算失败从 64 降到 23；首 30 PR 中 OpenSpec +7.79、cc-sdd +10.72 个百分点，Spec Kit −3.58。
- 但增益主要来自“原先失败的运行恢复了”，不是同一批成功任务上的判断力全面提升；micro recall 仍只有 5.82%–13.02%。

### 第四幕：判断与下一步（2 页）

- 已修：工具入口、规划路径、结构／身份校验、草稿收尾、任务口径、检索字段与排序。
- 未证：同环境 D/E 对照、68 个未参与调优 PR 的泛化、真实 token 收益。
- 下一步：先做匹配环境实验，再决定是否加关系／新事实；不把开发集收益写成普遍结论。

### Slide 1｜封面

**标题：** 从开发任务到待更新测试：无实现 diff 条件下的方法级定位

**讲稿：**  
“这次汇报的问题是：实现代码还没写，只给任务描述和当前仓库，能不能先找出哪些已有测试需要改。我会先讲任务和评价，再讲三类基线，最后讲测试意图增强目前走到了哪一步。”

### Slide 2｜任务定义：输入里没有本次 diff，输出必须落到方法

**标题：** 我们定位的是“需要维护的已有测试方法”，不是“相关测试”

**页面内容：**

| 项目 | 定义 |
| --- | --- |
| 输入 | 开发任务描述（PR title/body 或 issue）＋任务开始前的 base 仓库＋当时可见历史 |
| 不允许 | 本次实现 diff、最终测试 patch、隐藏 gold、事后评论 |
| 输出 | 已有测试的 `path::qualified_name` 排名／集合，附“为什么需要改”的依据 |
| 中间结果 | 文件级定位；最终目标是测试函数／方法级 |
| 允许的空结果 | 信息不足时可以“不确定”或空输出，但空输出不等于正确 |

**图表：** 一个三层漏斗：`任务描述 + base 仓库 → 候选测试 → 需更新判断 → 方法级输出`。

**讲稿：**  
“这里最容易混淆的是‘相关’和‘需要更新’。一个测试调用了被改的函数，只说明它相关；它可能仍然通过、断言仍然正确。我们的标签是开发者实际修改过的已有测试方法，这是代理标签，不是完备真值。”

**证据：** `context/purpose/final-goal.md`；`context/decisions/testcase-localization-v1.md`。  
**限制：** 开发者实际修改不等于“所有本应修改的测试”；新增、删除、纯改名单独记录。

---

### Slide 3｜为什么难：三个缺口，而不是一个检索问题

**标题：** 词汇、结构、必要性：三层缺口决定单一方法不够

**页面内容：**

1. **词汇缺口**：任务说“支持 HTTP/2”，测试名可能叫 `test_downloader_slots`；标题／正文与测试源码用词不一致。
2. **结构缺口**：测试行为分散在 fixture、基类、mock、helper、参数化里；只看方法正文会漏掉准备条件和隐式依赖。
3. **必要性缺口**：相关 ≠ 要改。生产内部重构、行为等价改写、共享 helper 修改，都可能让测试继续有效。

**图表：** 三个同心圆或三列卡片；每列配一个真实错误类型（不展示 gold 正文）：
- 词汇：宽泛 OR 查询把精确符号稀释；
- 结构：类合并 / 迁移导致方法身份混淆；
- 必要性：把“行为没变”误判为“方法内容不用改”。

**讲稿：**  
“如果只做检索，能解决第一层；如果只做 SDD，能碰第二、三层，但运行成本和稳定性不可控。我们的增强思路是把结构和行为证据先整理好，再让 SDD 在固定预算内判断。”

**证据：** `context/methodology/test-localization-methods.md`；`TEST_INTENTION_COMPACT_FIRST30_ANALYSIS.md` 第 3–7 节。  
**限制：** 这三个缺口是分析框架，不是已经量化的因果分解。

### Slide 4｜研究地图：四类链路，不能混成一次实验

**页面内容：**

| 链路 | 回答的问题 | 当前状态 |
| --- | --- | --- |

### Slide 7｜基线解读：召回不是瓶颈的全部，候选质量才是

**标题：** Top-k 越大，召回上升但精度必然下降；真正的问题是“候选池里有没有目标”

**页面内容：**

| k | Jina Macro Recall | Jina Macro Precision | Jina 命中目标 | 解读 |
| ---: | ---: | ---: | ---: | --- |
| 50 | 48.29% | 4.23% | 203/1,145 | 首屏质量最好，但只覆盖约一半目标 |
| 100 | 54.60% | 2.95% | 283/1,145 | 召回继续上升，精度腰斩 |
| 200 | 64.52% | 2.09% | 401/1,145 | 仍有约 35% 目标不在前 200 |

**页面结论（建议用大字）：**
- 检索解决“候选召回”，不解决“更新必要性”。
- 词法方法与向量方法差距有限；继续换检索器，边际收益可能小于补结构证据。
- 需要把“候选池召回”和“最终选择”分开报告。

**图表：** Recall–Precision 曲线（k=50/100/200），或“漏掉的目标数”柱状图（1,145 − 命中）。  
**讲稿：**  
“如果目标是 64%，那前 200 里还有 744 个目标没出现。后面的 SDD 再强，也找不回候选池里没有的测试。所以增强第一步不是换更大的模型，而是让测试行为更容易被检索到。”

**证据：** 同上；`context/workflows/test-retrieval.md`。  
**限制：** 不同方法的截断与编码策略不同；本页只做同范围描述，不做统计显著性声明。

### Slide 9｜增强思路：把“测试意图”变成可检索、可回查的材料

**标题：** 不是给 SDD 更多文字，而是给它“结构化行为 + 按需证据”

**页面内容（流程图）：**

```text
固定 base 源码
  → AST 静态目录（文件 / 类 / 测试 / 场景）
  → 提取共享 fixture、helper、mock、断言、调用、条件
  → 独立语义生成（失败则静态回退）
  → 按 base 冻结的 test intention 表示
  → 精简摘要 + 分页读取器（search / show / facts / source）
  → 三种 SDD 的新 Detect 轮次
  → 全部目标终结后，宿主机评分
```

**页面要点：**

| 设计选择 | 原因 |
| --- | --- |
| 一个源码方法可有多个场景 | 一个测试常覆盖多个输入／异常路径 |
| 静态事实与模型解释分开 | 模型摘要不是行为证明；回退项保留 `STATIC_FALLBACK` |
| 全仓可搜索，不做文件硬筛选 | 避免第一跳错误阻断召回 |
| 材料按 base 冻结、三 SDD 共享 | 同 base 可比；不按各 SDD 历史表现定制 |
| 生成与 Detect 分开计费 | 文件落盘不耗 Detect token，读入上下文才耗 |

**图表：** 上面流程图的图形化版本；右侧小卡片示例（脱敏，不展示 gold）。  
**讲稿：**  
“核心不是让模型读更多，而是让它先看到‘这个测试在验证什么’，需要时再展开源码。我们保留静态事实和模型解释的区分，避免把一句生成的话当成程序行为。”

**证据：** `context/workflows/test-intention.md`；`TEST_INTENTION_DESIGN.md` 第 2–4 节。  
**限制：** 语义生成有错误和回退；静态解析不证明运行行为；表示构建本身有成本。

### Slide 11｜诊断：预算不是花在“找答案”，而是花在找目录、修工具、读大段材料

**标题：** 90 份轨迹显示：85/90 搜过规划目录，88/90 出现工具错误，读取量是成功组的约 1.8 倍

**页面内容：**

| 观察 | 数值 | 说明 |
| --- | ---: | --- |
| 搜索过规划目录 | 85/90 | 不等于每次都致败；需区分首次定位与重复查找 |
| 出现工具错误 | 88/90 | 文本信号；严格要求非零退出且明确错误后涉及 64 项 |
| 失败组平均工具输出 | 464,025 字符 | 成功组 263,892 字符 |
| 失败组意图相关输出 | 276,424 字符 | 成功组 114,746 字符 |
| 90 份日志命令数 | 6,099 次 | 总输出 18,541,522 字符 |
| 意图材料输出占比 | 15.89% | 流程材料（尤其 Spec Kit）占比更高 |

**页面案例（脱敏）：**
- OpenSpec／PR7879：第 82 行已指出目标行为，随后仍查目录、schema、工具入口；第 148 行一次命令返回 382,993 字符，第 150 行才创建 change，随后预算耗尽。

### Slide 14｜结果分解：增益主要来自“恢复完成”，不是同一批任务判断力全面提升

**标题：** 把总差值拆成“两次都成功 / 原失败本次成功 / 原成功本次失败”

| --- | ---: | ---: | ---: | ---: | ---: |
| OpenSpec | +6.07（19 PR） | +5.17（5 PR） | −3.45（2 PR） | 0（3 PR） | **+7.79** |
| Spec Kit | 0.00（12 PR） | +7.39（7 PR） | −10.97（6 PR） | 0（4 PR） | **−3.58** |
| cc-sdd | 0.00（9 PR） | +19.34（9 PR） | −8.62（5 PR） | 0（6 PR） | **+10.72** |

| 指标 | OpenSpec | Spec Kit | cc-sdd |

**页面结论：**
- cc-sdd 的 +10.72 几乎全部来自“原先失败的 PR 现在有结果”，两次都成功子集净变化为 0。

### Slide 15｜错误结构：误报集中在少数结构性任务

**标题：** 提高 precision 的优先方向是“方法身份与结构”，不是继续润色行为摘要

### Slide 17｜当前结论：五条可以说、四条不能说

**标题：** 机制可行、部分改善、因果未定

**可以说：**

1. 已建立可复现的 98 PR、1,145 方法级目标数据与双粒度评价协议。
2. 四种检索基线完成同范围比较：Jina Recall@200 最高 64.52%，但候选精度约 2%。
3. 三种 SDD 直接定位有判断能力，但运行失败是主要瓶颈之一（35/90）。
4. 完整证据包因读取负担导致 64/90 预算失败；精简表示把意图材料读取字符降 85.75%、预算失败降到 23。
5. 首 30 PR 中 OpenSpec 与 cc-sdd 的 macro recall 分别 +7.79、+10.72 个百分点；但增益主要来自恢复完成，Spec Kit 下降 3.58。

**不能说：**

1. “测试意图表示让三种 SDD 全面变好。”——Spec Kit 下降，micro 仍很低。
2. “增强带来的是语义判断力提升。”——未做同环境 D/E 对照，恢复完成是主要贡献。
3. “检索 Recall@200 就是最终定位准确率。”——一个是固定 k 候选召回，一个是无固定 k 的最终选择。
4. “30 PR 的结果可以推广。”——30 PR 已用于开发诊断；泛化要看 68 个未参与调优 PR。

**图表：** 左右两栏“可以说 / 不能说”，用颜色区分；底部一行“下一张：如何把因果补上”。  
**讲稿：**  
“如果只记一张幻灯片，我希望是这张。我们已经把工程和证据链打通，也有部分正结果；但现在的证据还不足以支持‘方法全面有效’。”

**证据：** 综合上述各页。  
**限制：** 所有数字都有日期与协议版本；不能脱离范围引用。

## 6. 答辩／提问准备

### Q1：为什么不用现成的 RTS／覆盖率工具？

**答：** 它们回答“代码变了要重跑哪些测试”，我们要回答“任务要求下哪些旧测试需要维护”。关联、覆盖、重跑只是候选证据；测试可能仍然正确，也可能因接口／mock／注解变化而需要改。我们可以借用覆盖映射做候选，但不能直接把 RTS 结果当标签。

### Q2：1,145 个目标是怎么来的？可靠吗？

**答：** 来自 merged 且 CI success 的 PR 中开发者实际修改的已有测试方法，按 base 身份对齐，排除新增、删除、纯改名和 AST 不变的机械变化。它是可观察的代理标签，不是“所有本应修改的测试”的完备真值；分歧需要人工复核。

### Q3：为什么检索 precision 只有 2%，是不是方法很差？

**答：** 固定 k 下 precision 的分母是 k。平均每个 PR 约 12 个目标，前 200 个候选的理论上限也只有约 6%。2% 说明候选池很稀疏，这正是需要“候选召回 + 二次判断”而不是“检索即答案”的原因。

### Q4：精简版 OpenSpec 和 cc-sdd 涨了，为什么还说不能证明有效？

**答：** 因为涨幅主要来自原先失败的运行恢复：cc-sdd 两次都成功子集的净变化是 0，+10.72 全部来自“原失败→本次成功”和少量回退。没有同环境直接定位组对照，无法把“完成率提升”与“表示提升判断力”分开。

### Q5：Spec Kit 为什么下降？

**答：** 6 个“原成功、本次失败”的 PR 贡献 −10.97 个百分点，其中 2 个是 API 余额不足，4 个是预算耗尽；这些 PR 原来命中的测试本轮按零分。不能简单说“Spec Kit 不适合”，要先修复运行条件再做匹配对照。

### Q6：micro recall 为什么这么低？

**答：** 目标分布高度集中：PR7808（175 个目标）和 PR7968（100 个目标）合计占 361 个目标的 76.18%。这两个大 PR 仍然困难，所以 macro 上涨与 micro 低可以同时出现。我们同时报告两者，不用 macro 掩盖大任务。

### Q7：P1 的 37.64% 是不是说明检索已经很好？

**答：** 不是。P1 衡量的是“首个检索页面完整展示的候选召回”，不是最终选择；而且微平均集合覆盖只有 41.83%，排序找不回根本没进入匹配集合的测试。它是阅读入口的改进证据，不是 SDD 准确率。

### Q8：下一步最大的风险是什么？

**答：** 把开发集上的调优收益误当成泛化收益。30 个 PR 已参与诊断和设计，下一步必须在 68 个未参与调优的 PR 上、用预先固定的指标和预算验证；同时以 PR 为单位做配对分析，不能把 90 个目标当独立样本。

### Q9：为什么不直接上更大的模型／更长的上下文？

**答：** 第一版完整证据包已经证明“更多材料”会先把预算耗尽。当前瓶颈包括工具入口、输出路径、schema 和检索排序；在这些没修好之前，加模型或加长度无法区分收益来源。P0/P1 已先修这些地基。

### Q10：这项工作的贡献是什么？

**答：** 三点：① 一个无实现 diff、方法级、带隐藏 gold 隔离的测试定位任务与评价协议；② 同范围可复现的检索与 SDD 基线，以及失败／成本证据；③ 测试意图表示与精简阅读机制，并用轨迹分析说明“完成率收益”和“判断力收益”必须分开评价。

## 7. 措辞与事实边界

### 建议使用的措辞

- “在当前 30 个开发 PR、当前模型与预算下……”
- “macro recall 提高，但主要来自完成率恢复……”
- “检索基线提供候选召回，不直接等于最终定位。”
- “这是阶段性证据，因果对照尚未完成。”
- “失败按零分保留；无正目标单列。”

### 避免使用的措辞

- “我们的方法全面优于基线。”
- “Recall@200 达到 64.5%，所以定位准确率是 64.5%。”
- “精简版让三种 SDD 都提升了。”
- “30 个 PR 证明了方法有效。”
- “token 成本下降了 85.75%。”（那是字符，不是 token）
- “检索 precision 低是因为模型不行。”（固定 k 与目标稀疏是结构性原因）

### 数字引用时必须带的限定

| 数字 | 必须说明 |
| --- | --- |
| 98 PR / 1,145 目标 | 开发者实际修改的代理标签；96 个可评分，2 个无正目标 |
| 64.52% | Jina 的 Macro Recall@200，固定 k 候选召回 |
| 2.09% | Jina 的 Macro Precision@200；固定 k 下分母为 200 |
| 44.80% 等 | 30 PR 原基线 macro recall；35/90 失败计零 |
| +7.79 / −3.58 / +10.72 | 精简版 vs 原基线；每条件一次运行；未做同环境因果对照 |
| 85.75% | 意图相关命令输出字符降幅，不是 token |
| 37.64% | P1 首屏完整展示候选的 macro recall，不是最终定位 |
| 53,249 | 22 个 base 的版本内记录累加，不是单仓去重测试数 |

## 8. 一页纸备用总结（可做 handout）

**问题：** 无本次实现 diff，仅凭任务描述与 base 仓库，定位需要更新的已有测试方法。

**数据：** 98 个 Scrapy PR，75 个 base，1,145 个方法级代理目标；30 PR 开发集，68 PR 留作泛化。

**基线：**
- 四种检索：Jina Recall@200 64.52%，但 Precision@200 约 2%。
- 三种 SDD：macro recall 32.76%–44.80%，35/90 失败。

**增强：**
- 完整证据包：64/90 预算耗尽，指标下降。
- 精简表示：读取字符 −85.75%，预算失败 64→23。
- 首 30 PR：OpenSpec +7.79、cc-sdd +10.72、Spec Kit −3.58 个百分点。
- 增益主要来自完成率恢复；micro recall 5.82%–13.02%。

**判断：** 机制可行、部分改善、因果未定。

**下一步：** 同环境 D/E 对照；68 PR 泛化；按 PR 配对区间；只在剩余错误支持时加关系／新事实。
