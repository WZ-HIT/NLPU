## 1. 这一步交付什么

先把允许的 base 源码整理成可检查的静态记录和阅读页，准备小批模型输入样例。用真实输入规模说明调用怎样分批、哪些内容被省略，以及预算需要如何设置。

本卡保留静态阶段的具体要求。后续授权已覆盖首批 30 个 PR × 三种 SDD 的模型生成、必要的一次格式修复和增强定位；其余 68 个 PR 不在这次运行中启动。

## 2. 输入及来源

- 方案一已有的 98 个 PR 配置和对应 base 快照。
- 从允许的 base 源码重新构建符号与测试信息，保留来源版本、源码位置及内容校验码。
- 宿主机已有清单可以用于核对数量和身份，不将它直接变成实验 Agent 的新增输入。
- 不读取原始 PR 构建记录、隐藏答案、最终测试补丁、方案二的生产定位结果或已有逐测试预测来选择样例、生成表示或调整方法。

优先新增独立的 `experiment/test_intention/` 模块和对应离线测试，更新本任务卡与上游设计文档。实现入口和验证结果随首批实验记录更新。

首批接入只为新配置增加可选表示输入，旧配置默认行为不变；历史冻结轮次和正式 context 不改动。当前工作区有本任务开始前已有的修改，不能覆盖或计入本任务交付。

## 4. 原型需要做到什么

1. 识别文件、类、测试方法及源码范围，输出与已有方法身份规则的差异。
2. 建立跨文件代码目录，提取导入、调用、继承和共享准备内容，并保留未解析引用。
3. 提取输入表达式、配置、mock、断言和基本条件联系；将场景划分保存为候选，区分语法事实与待解释内容。
4. 按共享上下文组织小批输入，记录该批完整材料、引用和校验码，为后续缓存与分批提供依据。
5. 输出 JSON 静态记录、Markdown 阅读页和未解析／截断报告。尚未完成语义生成的字段明确标记状态。
6. 在小样例中展示跨 base 复用的判定：相关输入完全一致时可复用，任一生成输入变化时重新处理；源码位置重新绑定。

不要求原型恢复所有 Python 动态行为。重要的是可支持范围清楚、证据能查到、未支持情况不被写成确定事实。

## 5. 样例怎样选

从允许 base 中按源码结构选择少量方法，覆盖普通断言、共享初始化、fixture/helper、mock、参数化、多个场景和异步检查等情况。抽样规则与实际样例清单一同记录，不依据旧定位表现或隐藏答案挑选。

对于只处理了部分方法的文件，文件概览标明部分覆盖。模型输入中每项引用都能在本次提供材料中查到。

具体展开参数和分批大小先形成带理由的样例配置，并报告省略内容。这些原型参数不自动成为正式实验的冻结参数。

## 6. 怎样检查

- 用人工构造的小型代码检查别名、同名定义、嵌套函数、继承、fixture、mock、参数化和断言关联。
- 检查跨版本缓存不能忽略准备代码、同批测试、提示词或模型配置的变化。
- 检查模型输出校验器的规则：格式、身份、引用；最多一次修复的状态，以及失败后的静态回退记录。此处使用合成响应，不调用模型。
- 在真实 base 小样例中核对身份、来源、断言覆盖及阅读页链接；不执行被分析项目。

测试使用项目可用的 `python3 -m unittest`。具体命令随新增模块与测试一起提供，不在模块尚不存在时宣称检查已通过。

## 7. 成本材料需要说明什么

- 原始条目数、按共享上下文形成的批次数、完整输入一致时可复用的数量。
- 每批输入的大小分布、过大输入如何拆分，以及输出预留。
- 若有可验证的目标模型计数方式，报告 token 估算；否则明确报告字符数和估算方法，不将其冒充精确 token 数。
- 展示样例生成的调用上限、修复预留、时间与费用上限建议，以及全量构建成本的估算区间。

正式预算依据这些材料确定。任何价格或模型服务限制如需使用，另行核实其来源与时间，不能从上下文容量推导总费用上限。

本阶段完成不等于已生成全量 test intention，也不等于增强定位实验已启动或取得指标提升。
