# 为什么加入test intention后没有获得稳定的定位增益

2026-11-03。分析原30PR、三种SDD的已封存结果；扫描本轮90份Agent执行日志，并细读8个代表性任务的公开进度、工具命令和输出。未调用模型，未修改预测或标签，未读取其余68PR标签。

目前可以确认：完成率明显改善，定位质量的变化仍不一致。更关键的是，本次同时存在语义意图覆盖不完整、找到后排除正确候选、根据过宽范围批量选择等不同问题。不能统一归因为“意图文档太长”或“Agent没有使用意图”。

## 1. 最大的新发现：多数目标条目没有生成语义意图

全库有53,249条跨base的测试记录，其中11.78%是静态回退。但对这30PR的361个方法级目标条目重新核对后：

| 状态 | 目标条目数 | 占比 |
| --- | ---: | ---: |
| GENERATED，有模型生成的语义意图 | 165 | 45.71% |
| STATIC_FALLBACK，只有静态回退 | 196 | 54.29% |

这些数量按PR×方法计数，不表示跨PR互不重复的独立源码方法。三种SDD获得相同base表示，所以不能再把361乘三当成独立覆盖证据。

进一步读取196个目标条目对应的原始生成缓存：182个条目的错误为`Configured generation request or cost ceiling reached`；14个为`Scenario evidence must reference own test and supplied context`。它们分别关联69个和6个不同缓存记录，不能把182个条目说成182次失败请求；上限错误也不能进一步区分为请求数量还是费用哪一项先到达。

PR7808尤其严重：175个目标中172个为STATIC_FALLBACK，只有3个有语义意图。172个中，171个对应生成上限错误，1个对应证据引用校验失败。抽查的回退卡片显示`goal: null`，输入、mock、场景均为空，仍保留源码身份、静态依赖及回查入口。

这说明“全部测试都有结构化记录”并不等于“全部测试都有语义意图”。P1/P2已经让回退记录的已有事实进入搜索，并补充新静态字段，但没有重新生成这些缺失的语义意图。不能把本轮视为完整语义增强的检验。

**确定性：**上述覆盖和缓存原因已核实。缺失是否造成每个具体漏检仍未知，因为Agent也能阅读源码，且原始直接定位同样没有这些摘要；它解释了大量目标实际上未获得预期增强，不能单独解释所有分数下降。

## 2. 行为描述与更新目标之间还缺少一层判断

原模板的操作、输入、mock、条件和预期主要回答“测试目前检查什么”。定位任务还要回答：任务会影响测试中的哪一个构造、引用、断言、注解或配置假设；该影响为什么需要修改这个方法本身。

在行为不变的维护任务中，这两种问题差别很大。例如类合并后，输入和期望结果可以全部不变，但保留方法中的构造写法仍可能修改。将行为描述再压缩或补充更多输入，并不会自动补上这种对应关系。

具体证据：

| 本轮任务 | 已看到的证据 | 最终决定与标签结果 | 支持的判断 |
| --- | --- | --- | --- |
| OpenSpec／PR8002，合并测试类 | 第49行工具输出包含3个目标方法完整相关代码及`self.extractor_cls`调用；第60行进度已识别基类与具体类两层结构 | 第121行起认定只是搬移、行为不变；最终空集，漏3个目标 | 已读到目标，仍把行为不变推成现有方法不用改；不能归为单纯检索遗漏 |
| OpenSpec／PR8040，nested selector类型推断 | 第64、69行展开两个正确目标的意图，第76、78行读取场景，第100行再次输出源码 | 第115行起判断现有预期仍有效；最终空集，漏2个目标 | 意图确实使用了，问题出现在变更影响判断；两条目标都有GENERATED意图 |
| OpenSpec／PR8022，signal handler日志 | 第40行输出包含正确目标`test_signal_kill_reactorless_without_main_task`及其mock调用断言 | 后续集中于共享helper的日志检查，最终空集，漏1个目标 | 找到目标定义不等于正确理解其受影响断言；缺少对这个目标为什么无需改的逐项核查 |
| OpenSpec／PR7808，统一构造方式 | 已调查`build_from_crawler`、`from_crawler`与配置组件 | 第108行以保留原接口／断言为理由输出空集，漏175个目标 | 除语义覆盖缺口外，也存在维护修改与行为保持之间的判断缺口 |

这些是对公开决定及工具证据的诊断，不把模型公开解释当作完整内部推理，也没有检查未来实现来反推当时必然能得到答案。

公开提示已说明行为不变也可能有方法内容修改，但同时要求“必须有证据证明方法需要编辑”，并举了内部重构接口不变不能仅凭相关性选择的反例。短PR描述下，Agent仍经常把后一条解释成严格的行为失效标准。这里只能说提示、任务信息与判断标准之间存在张力，不能证明是某句提示单独造成了下降。

## 3. 另一端是把维护线索扩大为批量选择

| SDD | 本轮误报总数 | 主要来源 | 该来源占误报总数 |
| --- | ---: | --- | ---: |
| OpenSpec | 154 | PR8017：150个 | 97.40% |
| Spec Kit | 103 | PR8017：58个；PR7968：42个 | 97.09% |
| cc-sdd | 75 | PR7968：47个；PR7986：24个 | 94.67% |

OpenSpec／PR8017根据mypy配置定位文件，再用AST枚举其中未标注的测试，最后选择176个方法：26TP、150FP。工具日志可见它对“草稿与同一枚举规则是否一致”做了独立源码身份检查，但这仍不能证明枚举规则准确对应本次更新范围。

cc-sdd／PR7986则把“privatize its API”扩展到较广的HTTP/2实现表面，按类型注解中的类名引用选择27个方法：3TP、24FP。其第125行公开说明这是对“privatize”范围的解释；第152行再据此批量选择。

因此，补充注解、导入和继承等事实的价值取决于后续判断：“缺注解”不自动意味着本次要改；“引用了某API”也不能确定本次API私有化的具体边界。当前误报不是均匀分布，而是少数维护范围决策失准后批量放大。

**标签局限：**FP表示未命中当前从开发者补丁提取的标签，并不能单凭计数证明其余所有方法都不值得维护。它首先说明“预测未来实际修改集合”与“列出一种合理实现可能涉及的集合”存在差距。不能通过扩大标签或只强调相关性来消除这一差距。

## 4. 增加可搜索事实，尚未有效转化为先读到目标

此前固定公开查询、6,000字节首屏的离线比较已经显示：P1到P2，匹配集合覆盖151→181个目标，但首屏命中仅24→25。PR7968的匹配覆盖87→100，首屏仍为0；PR7808只覆盖10→13个目标，首屏仍为0。

这揭示两种问题：有些任务缺少覆盖，有些任务已经能匹配到目标，却没有把目标放在有限阅读预算内优先展示。上述单页离线查询不是Agent实际全部查询，不能据其0命中认定Agent运行一定没看见任何目标。

本轮90项都有reader命令；按每条完成命令中首个reader子命令统计，出现557次search、138次show、49次scenarios、53次facts、36次maintenance、52次source。54/90项至少显式使用过maintenance子命令或新事实字段查询。默认搜索也包含新字段，所以其余36项不能被称为完全没用新事实。

这些统计反驳了“意图根本没被读到”的笼统解释，但调用多也不代表获得了有效证据。PR8040多次查询、读到正确目标后仍输出空集，更支持检查决策层，而不是继续增加工具调用次数。

## 5. 两个大任务压住了micro指标

PR7808有175个目标，PR7968有100个，合计275/361，占76.18%。

| SDD | PR7808 | PR7968 | 两PR合计命中 |
| --- | --- | --- | ---: |
| OpenSpec | 成功、0/175 | 预算失败、0/100 | 0/275 |
| Spec Kit | 预算失败、0/175 | 成功、11/100 | 11/275 |
| cc-sdd | 成功、0/175，另1FP | 成功、18/100 | 18/275 |

因此，小任务改善或完成率上升可以推高macro指标，却很难显著抬高micro召回。对这两个任务，模型没有形成既能覆盖跨文件修改、又能限制批量误报的稳定决策。

预算仍影响结果，但已经不能解释全部问题：本轮9项预算失败确实记零；同时，OpenSpec和cc-sdd在PR7808都成功结束，仍没有命中。所以继续增加预算不能保证解决核心漏检。

## 6. 当前上涨有多少来自原失败任务现在有输出

下表将本轮相对原始直接定位版的macro召回差分解。每个数都是该组对全部29个正例PR均值的贡献，单位为百分点，三列相加得到总变化。

| SDD | 两版都成功时的变化 | 原失败、本轮成功 | 原成功、本轮失败 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| OpenSpec | −7.76 | +8.62 | −0.34 | +0.52 |
| Spec Kit | −7.14 | +13.69 | 0.00 | +6.55 |
| cc-sdd | −3.45 | +19.22 | −1.72 | +14.04 |

对比上轮精简TI：

| SDD | 两版都成功时的变化 | 上轮失败、本轮成功 | 上轮成功、本轮失败 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| OpenSpec | −13.79 | +6.90 | −0.38 | −7.28 |
| Spec Kit | +2.59 | +10.99 | −3.45 | +10.13 |
| cc-sdd | −4.07 | +7.39 | 0.00 | +3.32 |

相对原始版，三个SDD的共同成功子集都出现了平均召回净下降，整体上涨由原失败任务现在成功产生的正贡献抵消或超过。这个分解支持“不能把整体上涨直接称为意图提高了理解能力”。共同成功子集是事后选择，仅作诊断，不能替代全任务主指标或匹配消融。

没有在修复后的相同环境重跑无TI组；P0提示、工具、检索和表示同时变化，每组也只有一次运行。因此现在既不能声称已经隔离证明TI有效，也不能声称已经隔离证明TI有害。

## 7. 建议下一步怎么做

建议先验证两个机制，再考虑继续扩大表示或实验规模：

1. **修复表示的实际覆盖。**明确区分“有静态记录”和“有生成意图”，为缺失原因、请求／费用上限和校验失败建立可恢复记录。按公开base和统一规则检查全部失败记录；不能只补这196个已知正例。重新生成涉及模型预算，本次只诊断，不发请求。
2. **补上任务与源码敏感点的对应。**保留简短行为摘要，按需提供现有API／构造入口、mock目标、断言和固定常量、类型及配置假设、定义与继承归属。运行时说明“任务影响哪个点、为什么这个方法本身需改、依据是什么、哪里仍不确定”。这些事实从base独立构建，不把未来补丁写进意图。
3. **对大范围维护同时检查漏选和误选。**用配置和直接引用确定可解释的调查范围，但不把范围内所有未注解或同类方法自动全部选中；保留未知范围。先离线复核已发现的过严排除和过宽批量选择案例。
4. **区分检索失败与判断失败。**PR8040已展开目标、PR8002已输出目标源码，应先验证决策改动；PR7808的语义覆盖缺口及有限查询覆盖应先验证材料和检索。没有证据的阶段保持未知，不能只凭函数名出现就判断完整阅读。
5. **用匹配环境比较估计新增价值。**修复后的无TI、仅静态事实、静态事实加行为意图可作为候选分组，固定任务、预算和运行时；它们分别检验结构事实和语义摘要的贡献。当前用户没有授权追加这些模型组，本次不执行。30PR继续作为开发集，泛化结论另由未参与本轮调优的任务给出。

目前优先级最高的是“生成覆盖缺口”和“更新必要性的判断”，不是继续扩充全局关系图或反复压缩同一份摘要。
