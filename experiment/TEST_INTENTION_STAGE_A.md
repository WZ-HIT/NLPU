# 阶段 A：失败缓存恢复与补生成计划

版本：v3，2026-11-04。TI-15～17 已完成；TI-18 已改用 Plus 内含 Codex 实际生成，TI-19 待生成结束后完成。最新身份、实时入口与模型兼容性修订见[订阅生成记录](TEST_INTENTION_STAGE_A_CODEX.md)。以下保留此前 API 方案的离线设计和报价，作为未执行的备选，不代表当前需要支付该笔 API 费用。

这是实验分支的工作记录，不是正式 context 修改。范围继续为原 30 PR 涉及的 22 个公开 base；没有使用标签来挑补生成对象，也没有开始新的 SDD 定位实验。

## 已解决的恢复问题

旧生成器会直接返回失败缓存，重跑原命令不能补齐。本次新增独立入口 [recovery.py](test_intention/recovery.py)，读取原缓存，向新的执行目录保存恢复结果；不修改原 generation-cache，不将失败结果覆盖成看似成功的旧记录。

旧成功记录按原来的完整输入与生成配置复用。新的描述使用 `source-evidence-intention-2`，拥有不同缓存身份；不是把旧生成结果伪装成新版请求的缓存命中。同一新输入跨 base 只请求一次，发布时重新对应原源码位置。

执行账本在发送前持久化请求身份、尝试序号、预算预留和时间。恢复后分别处理：

| 状态 | 恢复行为 |
| --- | --- |
| 从未发送／预算拒绝 | 保留未完成状态，可在同一计划和既定额度内继续 |
| 已保存完整响应，但后续处理被中断 | 从已保存响应继续，不重新请求 |
| 请求开始，但没有可靠响应 | 保留未知消费预留，禁止自动重发 |
| 完整响应不符合结构或证据规则 | 最多一次明确的修复请求，仍失败则回退 |
| provider 输出未完成 | 记失败及用量，不自动加一次请求 |
| 生成成功 | 按结果哈希核查并复用，不重复消费 |

账本区分历史公式估算、历史未知预留、本轮已记录用量、本轮未知预留与本轮新增上限。重启会读取原账本；累计请求记录与累计估算保留，不能通过重启清零。

预算拒绝现在包含稳定的触发原因、时间、调用计数、请求上限、已用／预留额、下一请求预留与新增上限。未知消费不会被记为零。记账使用整数微元，避免浮点舍入放松边界。

同一计划绑定一个执行目录和一份额度；换目录重新启动或改变额度会被拒绝。执行目录有进程锁，数据库对输入包／尝试序号有唯一约束。初始化、预算检查与发送前记账使用事务，结果和响应使用原子写入。若估计预留小于已报告用量，会停止新派发并要求核查。

本版遇到额度不足时只停止；如后续另行增加额度，须保留已完成记录与账本制订修订恢复计划。不能另建空目录把相同包重新请求一遍。

## 证据校验保留了什么、增加了什么

[generation_contract.py](test_intention/generation_contract.py) 保留原来的完整包契约：测试集合不得缺失、重复或多出；每条测试必须有场景；每个场景必须引用自己的测试，只能使用该测试被提供的上下文。新输入直接列出每个测试的 `allowed_evidence_ids`。

错误报告包括具体测试、场景／字段位置和稳定错误码，例如：

```json
{
  "code": "EVIDENCE_OWN_TEST_MISSING",
  "path": "/tests/0/scenarios/1/evidence",
  "test_id": "tests/example.py::Example.test_value"
}
```

自己的 ID 缺失、引用同包其他测试的上下文、引用未提供 ID、字段类型错误和测试集合错误分别报告。修复仍使用同一源码证据，不自动补引用、不删场景，不把不合法输出当作有效部分保存。

已检查全部 **86 个历史引用失败包**。它们都没有保存原始失败回复，只有统一错误与尝试／响应身份。因此历史细分原因统一标为 `UNKNOWN_RAW_FAILED_RESPONSE_NOT_SAVED`，不能猜测是漏自己的 ID 还是混用了其他上下文。包清单与合法引用列表见 [evidence-errors.json](/data2/wangzuohit/NLPU-experiments/test-intention/stage-a-20261104-v1/plan-v4/evidence-errors.json)。

新的执行记录会保存可见 JSON 回复、精确错误及响应对应关系，便于之后复查；不保存 provider 私有推理。修复输入也有明确字节限制；超过限制直接保留失败，不截断 JSON 后假装修复。

## 原 API 备选方案的新增费用（未执行）

本次核查的[DeepSeek 官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)在 2026-11-04 列出 Flash 高峰无缓存输入 2 元／百万 tokens、输出 8 元／百万 tokens；计划统一按这两个价格保守记账，不假设缓存折扣或空闲折扣。provider 实际账单另行记录，公式估算不能充当发票金额。

| 预算项 | 金额 |
| --- | ---: |
| 历史公式估算，含早期探针 | 192.892308 元 |
| 历史未知消费预留 | 0 元；本批历史账本都有完整 usage |
| 本轮所有首次请求的保守预留合计 | 153.949832 元 |
| 所有新包都需要一次修复的保守预留上界 | 965.618960 元 |
| **本轮新增额度** | **尚待确定，未启动调用** |

预留按实际请求体 UTF-8 字节加固定封装余量估计输入，输出按上限估计；修复上界还按可见旧回复的最大转义长度估计，故上界远大于通常消费。实际响应到达后，使用报告的 token 用量按高峰公式更新记录；缺用量时保留整笔预留。

历史用量提供了另一种数量级参考：旧账本 3,032 条请求按同口径公式合计 192.892308 元，平均约 0.06362 元／次；772 次首次请求约 49.11 元。再套用旧批次约 12.43% 的修复比例，粗估约 **55.22 元**。旧失败包的复杂度、新提示和分包方式可能改变实际用量，因此这不是保证或账单预测。对应计算见 [cost-explanation.json](/data2/wangzuohit/NLPU-experiments/test-intention/stage-a-20261104-v1/cost-explanation.json)。

首次请求预留的 153.95 元中，输出部分约 101.19 元，假设每次都输出到 16,384 token；输入部分约 52.76 元，使用字节数估计 token。历史平均输出仅约 6,095 token／次，明显低于该上限。965.62 元则进一步假设全部包都修复，并携带最大可修复回复及最大 JSON 转义长度。两者用于检查最坏条件，不应被当作预计消费。

因此修订建议为**本轮新增费用上限先设为 100 元**，约为历史粗估的 1.8 倍。原提议 200 元不是必须的最低预算。并发请求只预留在途部分，响应后按实际 usage 更新；无需一开始同时冻结全部 153.95 元。达到确定的上限时停止，公布剩余，不自动提高额度。真实消费仍可能高于历史粗估，100 元不承诺补齐所有包。

历史 200 元是旧配置的边界，不能把它重置为本轮一笔新的 200 元。TI-17 原本要求“新增调用范围与额度确定后才进入 TI-18”；这是原 API 方案的预算状态；当前已切换为 Plus 订阅生成，此费用问题不再阻塞当前运行。

## TI-19 已准备，但还没有完成真实审查

[recovery_publish.py](test_intention/recovery_publish.py) 提供抽查、审查记录校验和独立版本发布入口。抽查规则在新增生成前固定：每个 base 各抽一个复用记录、一个新成功记录，再覆盖长测试、mock、条件、多场景、继承及剩余回退；各类按公开身份哈希排序选择，最多 50 个不同样本。某类没有记录时显式报告，不挑已知定位正确的测试。

抽查要逐条对照公开源码，写来源位置、判断和理由，检查预期、动作、条件、mock、共享准备、多场景与未知项。未经审查的模板不能通过发布；不得自动将全部样本设为接受。抽样说明绑定实际生成内容和状态，生成结果变化后旧审查会被拒绝。

质量不合格时隔离对应生成包，仍保留测试身份、静态事实和源码入口。发布将保留 P2 的静态维护数据库，重新构建短卡片、搜索和分页数据；文件主题改为静态导航，不启用模型生成主题。

新格式计划为 `compact-intention-v5`，会记录旧／新生成版本、父材料哈希、恢复计划和质量审查哈希、逐 base 实际生成及回退数。仍有回退就明确发布为部分覆盖。这里的“v5”目前仅在离线测试中验证，**真实的 22-base v5 尚未发布**。
