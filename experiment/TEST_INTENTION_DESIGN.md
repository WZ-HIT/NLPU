# 测试行为表示与静态解析方案

版本：第 9 版（用户授权先运行首批 30 个 PR 的增强组）  
日期：2026-11-01  
用途：说明已有测试如何整理、如何从代码提取信息，以及分析范围如何控制。  
状态：设计已确认，原型已实现；首批 30 个 PR 的执行进度及结果见 [首批实验记录](TEST_INTENTION_FIRST30.md)。设计本身不代表指标已经提升。

## 1. 我们要解决什么问题

给定开发任务描述和任务开始前的仓库，找回更多需要更新的已有测试，最终定位到测试函数或方法。

用户已明确区分两套基础方法：

| 方法 | 流程 | 与本次实验的关系 |
| --- | --- | --- |
| 方案一：直接定位测试 | 输入 PR title、body 和 base 仓库，由 SDD 直接定位需要更新的已有测试 | 本次增强的对象，已有结果作为参照 |
| 方案二：先定位生产代码，再定位测试 | 先运行一轮生产代码定位，再运行一轮测试定位 | 本次不增强、不作为方案一原始结果的替代 |

本次流程为：

```text
已有 PR title、body + 对应 base 仓库
  → 仓库中增加由该 base 构建的 test intention 材料
  → 三种 SDD 按方案一直接定位已有测试
  → 与方案一的已有结果逐任务比较
```

**复用已有实验数据和方案一原始结果，只运行新的增强组，不重跑原始组。**

为理解测试而读取 base 中相关的生产函数，属于测试表示构建的一部分；这不新增一轮生产代码定位，也不引入方案二产生的生产候选或规划输出。

一个测试方法的正文，往往不足以说明它在验证什么。它使用的对象可能在类的初始化方法里创建，输入可能由其他文件的辅助函数生成，网络响应可能被 mock 替换。只阅读方法正文，会遗漏这些信息。

本方案先把这些信息找齐，再整理成容易检索和核查的测试行为描述。本文使用“测试行为”描述代码实际构造和检查的内容；对测试意图的解释仍需有源码支持。

例如，原始代码里可能分散着配置、模拟响应和断言，整理后可以读成：

> 客户端遇到一次超时后再次请求，测试检查最终返回内容和请求次数。

这段话必须链接到相应代码。它描述的是测试的设置与检查内容，不说明测试已经运行通过，也不直接证明这个测试需要更新。

## 3. 最后会得到什么信息

### 3.1 文件、类、测试和场景

```text
测试文件
├── 文件主题与行为目录
├── 文件共享上下文
├── 测试类
│   ├── 类共享上下文
│   ├── 测试方法 A
│   │   ├── 场景 1
│   │   └── 场景 2
│   └── 测试方法 B
└── 独立测试函数 C
```

同一测试方法里的多条断言，可能共同检查一个场景；一个方法也可能先后检查多个场景。不能机械地按断言数量拆分。

每个场景保留以下内容：

| 内容 | 需要回答的问题 |
| --- | --- |
| 被测操作 | 主要检查什么行为？涉及哪个接口或对象？ |
| 输入 | 传入什么参数或数据？对象开始时是什么状态？ |
| 环境与 mock | 使用什么配置？哪些真实依赖被替换？替身返回什么？ |
| 前置条件 | 该场景开始前需要满足什么？ |
| 操作顺序 | 按什么顺序进行准备、调用和状态修改？ |
| 关键联系 | 断言检查的值来自哪里？哪些设置会影响它？ |
| 条件与预期 | 不同条件分别对应什么检查？ |
| 已有测试预期 | 实际检查了什么返回值、异常、状态或调用情况？ |
| 不确定项 | 缺少什么信息？哪里存在多种可能解释？ |

这里把原先“条件链”的内部内容展开了，具体 JSON 字段名称之后再定。

### 3.2 共享上下文

共享上下文是理解测试时需要补读的信息，常见内容如下。

| 内容 | 通俗说明 |
| --- | --- |
| setup / teardown | 测试前的准备与测试后的清理 |
| fixture | 框架提供给测试使用的数据、对象或资源，以及相关准备和清理逻辑 |
| helper | 测试调用的辅助函数，例如创建响应或构造输入 |
| 基类 | 测试继承的配置、初始化和辅助方法 |
| 公共配置 | 默认参数、环境变量、常量等 |
| mock | 替换真实依赖的对象或行为 |
| 参数化与限制 | 同一测试的不同参数，以及跳过或平台限制等条件 |

setup 表示准备步骤，fixture 是组织和提供这些准备内容的一种方式。两者可能重叠，记录时需要通过引用避免重复计算。

### 3.3 测试之间的联系

如果 A、B 使用相同的辅助函数，就保存：

```text
测试 A ──使用──→ 辅助函数 F ←──使用── 测试 B
```

这样既保留了联系，也能说明联系来自哪里。

“调用同一个接口”“使用同一个 fixture”主要依靠代码证据；“验证相同行为”“属于互补场景”通常还需要语义判断。两类关系分别标明来源。

共享依赖不表示测试之间有执行顺序，也不表示它们一定需要一起修改。

## 4. 静态解析具体怎样做

这里的“静态”指读取代码、分析代码结构，不导入和执行被分析的项目。第一版可以用 Python 的 `ast`，它能把源码拆成函数、类、赋值、调用、条件和断言等结构。原始代码同时保留，方便查证。

### 第一步：固定版本，列出已有测试

先确定允许使用的 base 版本。base 在本文中指开发任务实现前的仓库快照。

每个已有测试使用“文件路径 + 完整名称”识别，例如：

```text
tests/test_client.py::ClientTest.test_retry
```

对比现有定位方法时，沿用同一组测试身份。场景、参数组合和继承执行别名可以补充到表示中，但不因此增加计分单位。发现现有识别规则的遗漏时，单独报告，不在表示增强中悄悄改变候选集合。

记录读取文件的版本和内容哈希。哈希相当于内容校验码，用于确认之后读取的还是同一份源码。新增的辅助函数、生产代码和 `conftest.py` 等来源也要记录。

### 第二步：建立代码目录

先回答“定义在哪里”，记录每个文件中的类、函数、方法、参数、装饰器、导入和源码位置。

例如：

| 名称 | 定义位置 | 其他信息 |
| --- | --- | --- |
| `make_client` | `tests/helpers.py` | 参数、说明和源码位置 |
| `Client` | `app/client.py` | 基类、构造参数和方法目录 |
| `Client.fetch` | `app/client.py` | 参数、说明和源码位置 |

完整名称需要带所属模块或文件。不同文件都可能定义 `fetch`，不能仅凭同名就合并。

注释和说明文字可以辅助理解，但它们与实际断言分别保存；注释可能过期。

### 第三步：追踪名字指向什么

例如：

```python
from app.client import Client as HTTPClient

client = HTTPClient(timeout=3)
result = client.fetch("/items")
```

解析过程是：

1. `HTTPClient` 是导入名称的别名，指向 `app.client.Client`。
2. `client` 来自这个构造调用。
3. 根据可读的类定义、继承和后续赋值，寻找 `client.fetch` 的候选定义。
4. 如果对象可能被替换，或者存在多个定义，就保存这些可能性。

结果至少区分“找到唯一候选”“存在多个候选”“属于外部依赖”“未能解析”。找到唯一静态候选，也不等于证明运行时一定调用它。

第一版先支持常见的导入别名、局部赋值、简单对象构造、`self` 属性和可解析的继承。对于动态生成的属性名等复杂情况，保留表达式和未解析原因。

定义在测试内部的回调要单独记录。定义了函数，不代表其函数体已经执行；后续需要检查它是否被调用或传给其他接口。

### 第四步：找回测试使用的准备内容

解析 pytest 测试时，需要寻找可见的 fixture，包括测试所在类、模块和上级目录 `conftest.py` 等位置，并处理覆盖关系。

还要检查显式使用、自动生效的 fixture，以及 fixture 自己请求的其他 fixture。测试函数的参数不能全部当作 fixture，需要区分直接参数化、mock 注入等情况。fixture 的可见位置与其存活时间分别记录。

解析 unittest 测试时，寻找模块、类和方法层面的准备与清理，以及 cleanup 注册。若子类重写了准备方法，需要检查实际定义和基类调用，不能直接假定所有父类准备逻辑都会执行。

Twisted Trial 的异步结果检查也要单独支持。遇到无法解释的插件或自定义收集规则时，记录这一缺口。

### 第五步：提取输入、mock 和检查内容

| 信息 | 提取办法 |
| --- | --- |
| 输入 | 保存调用参数，并向前追踪相关变量的赋值 |
| 配置 | 找到关联的默认值、环境变量和对象属性设置 |
| mock | 保存替换目标、替代对象、返回值或异常序列，以及生效范围 |
| 检查 | 保存断言形式、被检查的表达式和期望表达式 |
| 运行条件 | 保存参数化、跳过和平台限制等设置 |

对于直接写出的数字、字符串和容器，保存其值。对于函数调用计算出的值，先保存表达式与来源，不通过执行它来取值。

检查内容既包括普通 `assert`，也包括框架断言、异常期待、mock 调用检查和异步结果检查。自定义检查函数要链接到实现；仅靠名称猜测的结果标为候选。

mock 的替换位置需要按代码中实际查找对象的位置解释。被 mock 替代的调用不能直接当作真实生产实现已执行的证据。

### 第六步：把条件、操作和预期联系起来

先读取代码中的顺序、分支、循环、异常处理和提前返回，记录哪些条件控制哪些操作。

再追踪被检查的值来自哪里。例如：

```python
timeout = 3
client = Client(timeout=timeout)
result = client.fetch("/items")
assert result.status == 200
```

可以记录：

```text
timeout 的赋值
  → 创建 client 时的参数
  → client 的调用
  → 调用结果 result
  → 对 result.status 的检查
```

这种追踪帮助发现断言附近真正需要的准备和调用。涉及全局状态、复杂对象共享和异步回调时，联系可能只能部分恢复，需要保留未知项。

原始测试仍然保留。没有被追踪到的代码不能直接判定为无关。

### 第七步：组织场景候选

程序可以根据参数化、`subTest`、分支和多组“准备—操作—检查”提出场景候选。多个断言共享一个操作结果时，也可以提出一个包含多项预期的场景候选。

这些结构不一定等于业务场景。模型随后结合代码判断如何归纳，并标明每个场景覆盖的源码。模型需要解释的重点是“这些操作和检查共同验证什么”，而不是重新猜测已能由程序提取的行号和表达式。

### 第八步：保存记录和关系

保存文件、类、测试、场景、辅助函数、fixture、生产接口和配置等记录，再用“属于”“使用”“调用”“继承”“替换”“检查”等关系连接。

直接调用与通过辅助函数间接关联需要区分，后者保留完整路径。每项记录都能回到源码；每个不确定关系都说明原因。

## 5. 一个完整例子

以下代码是假想示例，用于说明提取过程，不来自 benchmark 的真实目标测试。

```python
from unittest.mock import patch
from app.client import Client

def test_retry():
    client = Client(max_retries=2)
    with patch("app.client.transport.send") as send:
        send.side_effect = [TimeoutError(), b"ok"]
        result = client.fetch("/items")

    assert result == b"ok"
    assert send.call_count == 2
```

静态提取首先得到：

| 内容 | 代码证据 |
| --- | --- |
| 对象创建 | 使用 `max_retries=2` 创建客户端 |
| 调用 | 调用表达式为 `client.fetch("/items")` |
| 模拟目标 | `app.client.transport.send` |
| 模拟行为 | 依次提供超时异常和字节值 `b"ok"` |
| 预期一 | `result` 应等于 `b"ok"` |
| 预期二 | `send.call_count` 应等于 `2` |
| 数据联系 | `result` 来自 `fetch` 的返回值 |

理解 `fetch` 的具体对象来源、模拟位置是否与它关联，还需要查阅相关定义。静态阶段不会因为看到了 mock 配置，就认定该 mock 在运行中一定被调用。

在证据支持的范围内，模型可以归纳为：

> 配置首次调用超时、随后成功的模拟行为，检查请求结果和调用次数。

随后把“重试次数配置”“模拟行为”“返回值检查”“调用次数检查”分别链接到源码。两个断言共同检查这一过程，可以归为一个场景。

## 6. Q11 详解：先能找到，再决定补读多少

**Q11 的工作方式已确认：用户在阅读说明后回复“接受”。具体展开层数、大小和时间限制仍待确定，本文没有将其设为默认值。**

“全仓符号索引 + 按测试有界展开”可以改写成更直接的话：

> 先给允许的仓库源码建立一份代码目录，让跨文件定义能被找到；再为每个已有测试补读相关代码，明确读到哪里，以及在哪里停下来。

这里有三项不同工作：

| 工作 | 回答的问题 | 范围 |
| --- | --- | --- |
| 建立代码目录 | 某个类或函数在哪里？ | 允许的仓库源码范围 |
| 补读依赖 | 理解这个测试还需要哪些代码？ | 从每个测试出发，沿可解释的依赖查找 |
| 生成模型阅读材料 | 本次需要把哪些内容给模型？ | 从已保存记录中组织相关证据 |

### 6.1 “全仓”具体是什么意思

假设仓库有：

```text
tests/test_client.py       请求测试
tests/helpers.py           创建客户端的辅助函数
tests/conftest.py          公共测试资源
app/client.py              客户端实现
app/retry.py               重试规则
app/storage.py             存储功能
```

建立代码目录时，这些允许范围内的源码都能进入目录，包括不在测试旁边的 `app/retry.py`。

目录记录文件、定义名称、参数、说明、源码位置和必要的引用线索。它不等于已经理解每个函数的全部行为，也不等于建立了完整、准确的运行调用图。

全仓范围仍要明确排除版本控制目录、虚拟环境、生成产物和禁止输入。扫描失败或语法不兼容的文件需要列出，不能声称已完整覆盖。

### 6.2 “按测试”是什么意思

对已有候选集合里的每一个测试，都生成自己的行为表示。

例如，A 使用 `make_client`，就为 A 找回这个辅助函数；B 只验证解析字符串，就为 B 找回相应解析逻辑。两个测试可以引用同一份公共定义，无须反复解析和复制。

**这里不会先根据某个 PR 选出少量测试，再只分析这些测试。** 这种表示首先是针对 base 版本预先构建、可以跨任务复用的材料。

### 6.3 “展开”是什么意思

例如，测试只写了：

```python
client = make_client()
result = client.fetch("/items")
```

第一步找到 `make_client` 的定义。第二步读到它设置了默认重试参数并创建 `Client`。第三步根据需要继续查看 `Client.fetch` 及其使用的重试接口。

补读的过程可能形成：

```text
测试
  → make_client 辅助函数
  → Client 及 fetch 方法
  → 重试规则
  → 更底层的工具
```

每向后查看一层，都可能补充信息，也会增加解析和阅读内容。

代码目录让我们找到这些定义；依赖展开决定哪些定义需要进一步分析或摘要。

### 6.4 为什么要决定在哪里停下来

一个测试可能最终联系到网络库、日志、配置和通用工具。如果把所有能联系到的实现都反复塞进每个测试的描述，很多测试会变得庞大且相似，还会增加模型阅读成本。

但停得太早也会丢信息。例如默认重试次数藏在辅助函数后面，只读测试正文就无法准确描述环境。

所以需要分别控制两种范围：

| 限制 | 限制什么 | 达到限制后的处理 |
| --- | --- | --- |
| 分析展开限制 | 沿依赖继续解析多深、处理多少关联定义 | 保存已发现的引用，记录尚未继续分析的部分 |
| 模型阅读限制 | 一次给模型多少源码和摘要 | 完整记录保留；阅读材料标明省略内容，允许后续查阅 |

两种限制不能混为一谈。已经解析保存的内容，可以暂时不全部展示给模型；因为未继续分析而未知的内容，则不能被摘要成确定事实。

### 6.5 限制需要怎样记录

假设为了说明，某次分析只展开到 `Client.fetch`，未继续分析其调用的重试规则。记录应能让人读到：

```text
已读取：测试、make_client、Client.fetch
已发现：fetch 引用了重试规则
未继续分析：重试规则内部实现
原因：达到本次分析的展开限制
影响：关于重试规则内部条件的描述仍不完整
```

这个例子没有指定正式层数。实际限制可以考虑依赖类型、关联定义数量、源码大小和处理时间，并将配置一起保存。

准备方法、fixture、helper 和生产函数的作用不同，不必机械地使用同一展开策略。具体规则仍需结合样例确定。

### 6.6 会不会因此漏掉需要更新的测试

有可能漏掉较深的关联证据，但不应因此删除测试本身。

建议保留以下通道：

1. 每个已有测试仍保留自己的源码、直接提取的信息和索引位置。
2. 无法恢复依赖的测试保留不确定项，继续参加直接文本或语义检索。
3. 已知但未展开的关联保留引用，允许后续补查。
4. 不把“当前图里没有找到路径”当作排除测试的依据。

共同依赖也不自动把所有邻居推入最终 Top-k。已确认将关系扩展作为可单独启用的补充渠道，记录候选来源；与直接检索结果合并去重、统一排序后，仍按固定数量输出。具体排序规则需要另行设计并验证。

### 6.7 如果信息不够，怎样补充

在方案设计和开发样例上，如果发现很多测试的关键预期都藏在同一种辅助结构里，可以针对这种结构调整展开策略，并记录版本变化。

后续也可以设计“模型先读摘要，需要时沿引用补查源码”的流程，但其权限、阅读预算和比较方法需要单独确定。

正式比较前应固定策略。不能查看最终测试集答案后，不断修改展开规则，再把同一批测试上的上涨当作独立验证结果。

### 6.8 Q11 已确认的工作方式与待定参数

已确认采用“全仓建立代码目录、所有测试保留表示、相关依赖按明确规则补读”的工作方式。

这一决定不等于确定具体层数、长度或时间限制。这些参数应在理解样例和查看解析缺口后再定。

这一工作方式兼顾跨文件查找、信息复用和成本记录。分析展开限制与模型阅读限制分别设置；具体规则和数值仍需结合样例确定。

## 7. JSON 和 Markdown 怎样配合

JSON 保存完整记录和引用，包括源码位置、提取结果、关系、不确定项及分析限制。Markdown 从这些记录生成，展示文件概览、测试卡片和关系说明。

例如，多个测试引用同一个 fixture 时，JSON 中保存一份定义，各测试保存引用；阅读某个测试的 Markdown 时，可以展示该 fixture 的关键设置并链接到完整记录。

源码事实、模型解释和分析状态分别保存。例如：

| 类别 | 示例 |
| --- | --- |
| 源码事实 | 断言表达式是 `send.call_count == 2` |
| 语义解释 | 这个检查用于验证请求次数 |
| 不确定项 | 当前未能确定 `client` 的唯一类型 |
| 分析限制 | 已发现某个 helper，但没有继续读取其内部依赖 |

还需要区分“源码没有设置”“出现了但没能解析”“存在多个候选”和“因限制未继续处理”。这些情况不能统一写成空值。

本节示意不代替实际数据。当前实现的 JSON 字段与运行参数见 `experiment/test_intention/` 和首批实验的输入快照。

表示内容发生变化是本次研究的因素，应记录新版本，不能宣称与旧方法的候选文档完全相同。

## 10. 怎样给三种 SDD 的仓库提供这些信息

### 10.1 本轮补充的实验方向

### 10.2 当前三种仓库怎样组织

当前准备程序为三种方法分别创建任务前仓库副本。定位阶段在宿主机上的相对路径为：

```text
任务目录/runs/openspec/detect/workspace/
任务目录/runs/speckit/detect/workspace/
任务目录/runs/cc-sdd/detect/workspace/
```

容器内都显示为 `/workspace`，仓库本身只读；各方法另有可写的规划目录。准备程序会记录整个初始仓库的内容哈希，后续流程核对它是否变化。

因此，表示文件应在新实验的准备阶段纳入输入并一起冻结。向历史已冻结仓库直接添加文件，会改变其原有身份，不能用来代表一次独立的新比较。

### 10.3 建议的接入方式

Q14、Q15、Q16 已确认：同一 base 共享一份表示，首轮只增强并评价方案一中三种 SDD 的 Detect 定位阶段，SDD 自主查阅增强材料。测试代码更新阶段、额外生产定位阶段不属于首轮范围。

下面是已采用的首批接入流程。实际公共入口固定为 `/workspace/test-intentions/README.md`，新配置通过可选 `test_intention` 字段指定按 base 固定的清单：

1. 从允许的纯 base 源码生成测试表示，不读取 SDD 规划结果、实现后的代码或评价答案。
2. 同一 base 使用同一份生成产物，供三种 SDD 使用；不同 base 分别生成和校验。
3. 创建新轮次的三种仓库，在复制 base 与 SDD 初始化之后、计算初始内容哈希之前，加入表示文件。
4. 三种方法使用同一个阅读入口，例如 `/workspace/test-intentions/README.md`，再由入口链接到 JSON、文件概览和测试卡片。该入口在本次首批配置中固定。
5. 表示放在普通仓库目录中，随仓库只读提供，避免与各 SDD 可写的规划内容混在一起。
6. 在方案一的定位说明中用一致方式指出入口，说明可按需阅读并核查源码，保留全仓测试搜索能力；原始输入、输出身份和比较预算保持可核查。

这一方式可以让三种 SDD 获得相同的测试知识，分别按各自流程使用。模型或生成过程的差异就不会被混入三种 SDD 的方法差异。

三种仓库是各自获得一份相同内容的副本，生成成本则可以按 base 复用。只有在 base、生成配置和来源内容都一致时，才可视作同一份产物。

首轮评价关注已有测试方法的定位结果，同时记录生成表示所需的时间和模型成本，以及 SDD 阅读和使用这些材料的成本。增强表示不改变原始源码测试身份。

### 10.7 已确认的分批和失败处理规则

Q21 已确认：按同类或共享上下文的小组组织生成请求，共同提供准备代码，每个方法分别保存结构化结果。内容过大时拆批。每批方法清单、提供的上下文及生成配置都要记录，跨版本复用时核对整批完整输入。

Q22 已确认：对模型结果自动检查 JSON 格式、测试身份及源码引用。未通过时允许最多一次修复，修复仍未通过则不采用该条模型描述，保留源码与静态提取记录，明确标记“描述未生成”。测试继续保留在定位范围内，生成失败数量和静态回退覆盖率单独报告。

修复只针对同一批结果的已知检查问题，不读取评价答案。修复消耗计入生成预算，不自动无限重试。模型请求本身的网络故障如何处理仍需在执行配置中明确，不能默认为额外授权的反复调用。

自动检查能确认记录结构、身份和引用是否有效，不能单独证明语义解释正确。语义质量通过源码对照抽查，尤其检查是否遗漏预期、是否编造条件、是否混淆场景。
