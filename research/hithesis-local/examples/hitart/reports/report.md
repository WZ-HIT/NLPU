今天汇报的题目是“基于开发任务的测试用例更新目标定位与选择”。本课题面向一般 Python 项目的 Pull Request，也就是 PR，研究如何根据开发者提供的开发任务描述以及变更前的代码仓库，判断哪些已有测试文件可能需要随软件变更同步更新。

本次汇报将从研究问题、相关工作、实验流程、初步结果和后续安排五个方面展开。

## 第 2 页：研究问题与实验边界

本课题所说的自然语言，特指开发者提交 PR 时填写的标题和正文。标题通常概括变更主题，正文进一步说明问题背景、修改原因和预期行为。

方法可以读取两类信息：第一类是 PR 的标题和正文；第二类是 PR 合并前，也就是 base 版本的生产代码和已有测试。方法需要根据这些信息输出可能需要更新的测试文件路径，并保留判断理由和运行状态。

实验中必须隔离参考答案。PR 合并后的 head 版本里实际修改了哪些测试文件，只能在检测结束后用于评价，不能提前提供给方法。本文当前只判断“哪个测试文件需要更新”，不进一步定位文件中的测试函数、断言或具体修改位置，也不直接生成测试代码。

目前已经完成 30 个 Scrapy PR 的样本质检和初步检测，每个 PR 分别运行三种 SDD 方法，共形成 90 个检测目标。

**过渡：** 明确任务边界以后，下面介绍相关研究已经解决了什么，以及本文从哪里切入。

---

## 第 3 页：相关研究与本文切入点

与本课题相关的研究大致可以分为三类。

第一类是自然语言和代码的语义表示，例如 CodeBERT 和 UniXcoder。这类工作能够建立文本与代码之间的语义联系，为使用 PR 描述检索测试代码提供基础。

第二类是测试生成、改进和修复，例如 IntUT、FlakyFix 和 TestGen-LLM。它们说明大语言模型能够理解测试意图并生成或修复测试，但通常已经知道目标类、目标方法或者目标测试，重点是“怎样修改”。

第三类是代码与测试共同演化以及问题驱动的测试检索。COTE 研究生产代码与测试代码的共同变化，IssueExec 则先从 issue 文本检索相关测试，再利用测试执行定位生产代码。

现有工作较少直接回答一个更前置的问题：只根据 PR 自然语言和变更前仓库，应该更新哪个已有测试文件。因此，本文尝试把 SDD 生成的规格、设计和任务作为检测信号，在统一的文件粒度下评价不同方法。

**过渡：** 围绕这个研究空缺，整个实验按照下面五个步骤展开。

## 第 4 页：研究整体流程

这张图展示了研究的完整流程。

第一步是 PR 采集与样本质检，确保样本已经合并、版本完整，并且包含可复核的测试修改。

第二步是构造检测任务，把方法可见的输入和用于评分的参考文件分开保存。

第三步是执行多方法检测。目前使用 OpenSpec、Spec Kit 和 cc-sdd 三种 SDD 流程，后续还计划适配 IssueExec 的测试检索阶段作为对照。

第四步是统一文件级输出。不同工具的规划产物格式不同，需要统一解析为仓库相对测试文件路径，同时保存理由和运行状态。

第五步是评价与误差分析。通过文件级命中率、召回率和人工案例复核，分析方法为什么能够命中，以及为什么会出现误检或漏检。

**过渡：** 下面按照这个流程，先介绍样本是怎样获得的。

## 第 5 页：PR 采集与样本质检

项目首先从 ansible、matplotlib、pandas 和 scrapy 四个 Python 开源仓库采集 PR。

第一轮通过 `merge_quality` 和 `code_presence` 检查合并质量及代码变更情况，得到 938 个预筛选 PR。之后检查 CI 状态，排除明确失败或者状态不可确认的样本。

自然语言质量过滤使用标题、正文和提交消息的有效词数。当前阈值是：标题不少于 4 个有效词，并且正文不少于 14 个有效词，或者提交消息不少于 6 个有效词。提交消息在这里仅用于样本筛选，不进入后续 detect 输入。

最后核对 base 和 head 版本、测试文件修改、仓库可复现性以及重复样本。目前已经完成 30 个 Scrapy PR 的筛选和质检。这 30 个 PR 共包含 145 个按 PR 累计的参考测试文件，并形成 90 个“PR—方法”检测目标。

**过渡：** 得到合格样本后，还需要确保检测方法看不到历史修改答案。

---

## 第 6 页：构造检测任务并隔离参考答案

对于同一个 PR，实验构造两条彼此隔离的数据路径。

左侧是检测输入，也是方法可以看到的内容，包括 PR 标题、正文以及 base 版本代码仓库。右侧是参考标签，包括 head 版本中实际修改的测试文件，只能在最终评分时使用。

任务构造时会检查输入中是否意外包含 head 测试、测试差异或者 gold 文件路径。三种方法分别使用独立工作区，也不能读取其他方法的规划产物。

这样做的目的是还原真实预测条件。方法需要在变更答案不可见的情况下理解需求并定位测试，否则实验结果就不能说明方法是否具备目标检测能力。

**过渡：** 在相同的检测任务上，本文比较三种 SDD 工具的规划过程。

---

## 第 7 页：三种 SDD 工具及使用方式

本文选择 OpenSpec、Spec Kit 和 cc-sdd 三种公开的 SDD 工具。

OpenSpec 从变更提案出发，逐步形成规格、设计和任务。本文从 proposal、specs、design 和 tasks 中提取被明确提及或推断需要维护的已有测试文件。

Spec Kit 从自然语言规格出发，经过 plan 和 tasks 形成实施任务。本文主要分析 spec、plan 和 tasks 中关于测试维护的规划。

cc-sdd 使用 requirements、design 和 tasks 等阶段式产物描述变更，并支持项目约束和既有代码分析。本文从这些规划产物中识别测试更新目标。

三种工具都只运行规划或者 detect 阶段，不执行 implement 或 apply，不修改仓库，也不能读取 head 测试答案。本文关注的不是哪一种工具更会写代码，而是哪一种规划过程更有助于发现待更新测试文件。

**过渡：** 为了保证比较公平，三种方法使用统一的模型和运行配置。

---

## 第 8 页：多方法检测与统一运行配置

三种 SDD 流程接收完全相同的 PR 自然语言和 base 仓库。

实验统一使用 DeepSeek-V4.1-Flash，推理强度设置为 high。每次运行的 rollout token 上限为 10 万，时间上限为 2700 秒。一个 PR 和一种方法的组合构成一个检测目标，每个目标计划独立执行一次。

如果运行因上游服务中断等非方法因素失败，会通过显式重试恢复，同时记录尝试次数和失败原因。重试用于恢复原目标，不作为新的独立重复实验。

三种 SDD 方法最终产生规划文档和原始候选目标。后续计划适配 IssueExec 的测试检索阶段，使其接收相同输入并输出文件级候选，从而形成检索对照。

**过渡：** 由于各工具的原始产物不同，下一步需要把它们转换为统一结果。

---

## 第 9 页：统一为文件级检测结果

统一处理过程分为五步。

第一，从规格、设计或任务文档中解析候选测试目标。第二，把绝对路径、相对路径或者测试符号统一转换为仓库相对路径。第三，在 base 仓库中检查文件是否真实存在，并确认它属于测试文件。第四，对重复路径进行去重。第五，保留判断理由、无效路径、失败和运行状态。

这里也对应题目中的“定位”和“选择”。定位是从规划产物中发现可能相关的原始测试目标；选择是在定位结果上进行路径解析、存在性检查、测试文件检查和去重，形成最终有效候选集合。本文的选择是集合筛选，不涉及候选排序。

最终，每个检测目标都被转换为统一的“候选测试文件路径、判断理由和运行状态”。

**过渡：** 有了统一的文件集合以后，就可以与历史 PR 的实际测试修改进行比较。

---

## 第 10 页：评价与误差分析

对于某个 PR，记方法输出的候选测试文件集合为 (C_p)，历史实际修改的参考文件集合为 (G_p)，两者的交集为命中集合 (H_p)。

命中率等于命中文件数除以候选文件数，回答“方法给出的候选中有多少是历史上实际修改的”；召回率等于命中文件数除以参考文件数，回答“历史修改的测试中有多少被方法找回”。

实验同时报告 micro 和 macro 两种口径。micro 指标先汇总文件数再计算，容易受到大型 PR 影响；macro 命中率先逐 PR 计算再平均，更能反映不同 PR 上的平均表现。

除指标外，还统计有效输出、空输出、无效路径、错误和上游中断，并人工复核误检和漏检。需要强调的是，历史修改文件只是可观测的代理标签。一个文件没有在历史 PR 中被修改，并不一定说明它完全不需要更新。

## 第 11 页：初步检测结果

当前初步实验共包含 30 个 PR、90 个方法目标和 145 个参考测试文件。

OpenSpec 命中 56 个文件，共输出 136 个候选，micro 命中率为 41.2%，逐 PR 的 macro 命中率最高，为 62.3%。

Spec Kit 命中 46 个文件，共输出 90 个候选。它产生的候选最少，micro 命中率最高，为 51.1%，但召回率为 31.7%。

cc-sdd 命中 58 个文件，共输出 166 个候选。它找回的参考文件最多，召回率为 40.0%，同时候选规模也最大，micro 命中率为 34.9%。

这里需要说明运行边界。Spec Kit 有 4 个目标因上游 token 池中断而没有产生候选。为了保持 90 个目标的总体统计完整性，当前描述性结果将它们按未命中计入，同时标记为运行异常。另外还有 1 个 ERROR。因此，这张图反映的是当前全部运行记录，正式比较前仍需要恢复异常目标并重新计算指标。

从现有数据只能观察到三种方法在候选规模和参考文件覆盖之间存在不同取舍，还不能据此直接认定某一种方法更优。

## 第 12 页：典型案例

第一个案例是 PR 7918。这个 PR 修改 `ScrapyJSONEncoder` 对日期和时间的序列化方式，历史上修改了两个测试文件。三种方法都只输出这两个文件，结果均为 2 比 2。它说明当自然语言、生产代码和测试断言之间关系明确时，三种方法都能够准确定位。

第二个案例是 PR 7846。它为 Twisted 的 IDNA 辅助函数增加兼容处理，历史修改涉及下载器核心测试和共享 HTTP 下载测试基类。OpenSpec、Spec Kit 和 cc-sdd 的结果分别为 1/5、1/7 和 2/8。cc-sdd 找回了两个参考文件，但也给出了更多候选，体现了召回能力与人工核查范围之间的取舍。

第三个案例是 PR 7966。它的标题比较笼统，正文为空，历史上实际修改的是 `tests/test_utils_console.py`。三种方法分别给出 14、9 和 11 个候选，但都没有命中。这个案例说明，当自然语言缺少具体警告类型和受影响组件时，方法容易依赖仓库中的常见关联进行推断，最终产生系统性偏离。

综合三个案例可以看到，自然语言的充分程度、依赖分析范围和 PR 修改规模都会影响定位效果。

# 答辩时需要特别注意的口径

1. **自然语言的范围**：仅指 PR 标题和正文；提交消息只用于样本质量筛选。
2. **研究粒度**：只判断需要更新的测试文件，不定位断言，也不生成测试代码。
3. **定位与选择**：定位负责发现原始目标，选择负责路径校验、测试文件检查和去重。
4. **四个中断目标**：当前描述性统计按未命中计入，同时标记为运行异常；正式比较前需要恢复并重新统计。
5. **历史修改的性质**：历史修改文件是代理标签，未修改不等于一定无需更新。
6. **初步结果边界**：目前只能说明候选规模和覆盖程度存在取舍，不能直接宣布某种方法最好。
