#### 1. 研究意义

质量是软件的生命。然而,由于有限的开发时间和资源、开发人员知识水平 和项目经验的不足,开发人员往往不得不编写"临时的、不完整的、有缺陷的或 次优的代码"[1]。尽管在短期内可以缓解交付压力、加快产品发布,但从长远来 看,这类代码不仅会在性能、可维护性等非功能性指标(通常不会触发测试失败) 方面降低软件质量,还会在软件演化过程中不断累积维护成本,使开发团队在后 期付出更高的"利息"。研究人员形象地将这类代码比作软件技术债[1](即技术 债)。例如,使用 Java 语言时,在循环内部频繁创建和回收临时集合对象(例如, ArrayList)会导致额外的内存开销与频繁的垃圾回收,严重影响程序的性能,使 得软件在后续运行过程中持续消耗更多计算资源。近年来,研究人员关注开发者 明确承认并显式声明的技术债,即"自承认的软件技术债"(Self-Admitted Technical Debt,简称 SATD)[2]。例如,在 PyTorch 项目的源代码注释中,开发 人员描述相应的代码存在"克隆代码"这一技术债:"TODO: Deduplicate this with canonicalize\_dim"。由于 SATD 没有隐式的体现在代码结构和实现细节中,能够 准确、明确地反映开发人员所认可的技术债,为系统性地管理和研究技术债提供 了切入点,已成为研究技术债的主流媒介[4],因此后文提及的技术债均指 SATD。 随着软件行业多年高速发展,软件复杂性急剧上升、遗留代码规模不断扩大, 技术债问题日益凸显。据测算,2025 年,仅用于维护技术债相关代码的预算就 占美国 IT 总预算的 40%,并且开发人员有三分之一的工作时间花费在解决技术 债相关的问题上[5]。智能音箱公司 Sonos 由于长期积累的大量技术债,应用频 繁崩溃,严重影响用户体验,导致大量用户流失,股价下跌 25%,收入损失 2 亿 美元[6]。面对这些严峻挑战,如何高效、有效的修复技术债,已成为整个行业亟 待解决的关键问题。中国计算机学会软件工程专业委员会也将**"**大规模代码遗产 系统的优化与重构**"**列为三个首批发布的**"**软件工程重要研究问题**"**之一[7]。幸运 的是,近年来以 DeepSeek 为代表的大语言模型(Large Language Model,LLM) (草稿)请于提交后重新下载PDF的正式稿

的崛起,使得智能化修复技术债成为了可能。LLM 时代技术债的自动修复已经 成为了软件工程研究的热点。例如,即将召开的国际软件工程大会(ICSE'26) 将专门设置小组讨论"人工智能时代的技术债"[8]。因此,开展技术债的自动修 复研究正当其时,对于提高软件开发效率与软件产品质量具有重要意义。

修复技术债的目标是构造既不破坏原有功能也不存在技术债的代码补丁[9]。 由于技术债是"临时的、不完整的、有缺陷的或次优的代码",从形式上看,其 自动修复在一定程度上理应可以被视为程序自动修复问题的一个特例。近年来, 研究人员利用 LLM 的语义理解与生成能力,开始将 LLM 引入程序自动修复任 务中,在生成初始补丁后,构建"评估—优化"的迭代循环,提升补丁生成的质 量。例如,申请人前期的研究探索了 LLM 生成的测试用例对于程序自动修复的 影响[10]。通过向 LLM 提供缺陷描述及缺陷复现测试用例,LLM 不仅能够生成 候选补丁[11],还可进一步生成额外的缺陷复现测试用例,并将新增测试执行过 程中暴露的错误信息与运行轨迹通过迭代式对话机制反馈给 LLM,引导其逐步 调整生成策略,生成质量更高的补丁[12]。然而,这些方法仅仅关注了补丁的功 能正确性,其评估机制依赖测试通过与否,忽略了代码复杂度等技术债关注的非 功能性指标(不会触发测试失败),难以保证补丁中不存在技术债。 (草稿)请于提交后重新下载PDF的正式稿

尽管近年来已有研究关注技术债的自动修复,并初步探索了 LLM 在相关任 务中的潜力,但现有方法仍主要孤立地聚焦于技术债修复补丁的直接生成等单 一任务上。从程序自动修复的研究范式来看,"评估—优化"的迭代循环是提升 补丁质量的重要途径。若能够在技术债自动修复过程中,系统评估补丁(1)是 否消除了技术债、(2)是否保持原有功能,并将评估结果用于(3)迭代反馈引 导 LLM 生成补丁的过程,则有望充分发挥 LLM 在复杂修复任务中的能力,实 现更加可靠的技术债自动修复。然而,在将"评估—优化"迭代循环这一范式应 用至技术债自动修复场景时,仍面临一系列关键挑战:

挑战 **1**:(告警信息难详尽)在评估技术债修复补丁是否消除技术债时,技 术债告警信息要语义清晰、具备可操作性,以支撑 **LLM** 准确理解技术债并生成 高质量修复代码。在基于 LLM 的技术债自动修复场景中,补丁的质量高度依赖 于输入提示信息的表达质量。当缺乏明确的语义信息与可操作的修复建议时, LLM 难以理解技术债,仅能基于表面信息进行修复,容易生成看起来合理但实 际上失效的补丁,无法从根本上消除技术债,甚至可能在重构过程中引入新的技 术债,从而削弱自动修复方法的有效性。

![](_page_5_Picture_0.jpeg)

挑战 **2**:(意图测试易脱节)在评估技术债修复补丁是否保持原有功能时, 需要构建与修复目标匹配的测试体系,以支撑对 **LLM** 生成补丁的客观可靠评 估。技术债修复通常涉及较大规模的代码重构、接口调整或依赖关系重组,导致 既有测试用例难以直接复用。在缺乏与技术债修复意图一致的测试用例支撑下, 既有评估往往只能验证补丁的可编译性或有限功能正确性,难以系统评估技术 债修复补丁对软件功能正确性的影响,使得补丁质量评估存在明显不足,严重制 约技术债自动修复流程的可信性与工程可落地性。

挑战 **3**:(技术债依赖关系复杂)在利用 **LLM** 生成技术债修复补丁时,需 要充分考虑不同技术债之间的结构依赖关系,并据此推理合理的修复顺序。由于 技术债具有一定的关联性,对某一技术债的修复往往会产生连锁影响,甚至可能 需要多个技术债协同处理[4,13]。在缺乏系统性的依赖分析的情况下,LLM 难以 判断哪些技术债应优先处理、哪些修改需要联合完成、当前修复是否依赖前序结 构调整,容易形成碎片化、无序化的修复,导致修改范围频繁调整、补丁多次返 工与回滚,显著削弱技术债自动修复流程的整体效率。

为应对上述挑战,本项目提出"基于评估引导迭代优化的软件技术债自动修 复研究"的课题,着重研究如何协助 LLM 理解技术债内涵、测试修复意图、推理 修复顺序以生成高质量补丁,构建基于"评估—优化"的迭代循环,系统提升技 术债自动修复的准确性与可靠性。通过将依赖人工经验的技术债告警、修复与评 估过程转化为自动化流程,本项目显著降低开发人员的时间成本,提升工程效率。 同时,研究成果将有效缓解技术债积累带来的维护成本与性能损耗,增强软件系 统的长期演进能力,为面向非功能质量约束的程序自动修复与智能维护研究提 供新的技术路径与方法。 (草稿)请于提交后重新下载PDF的正式稿

#### 2. 国内外研究现状

本项目以技术债自动修复为核心,系统应对利用 LLM 构建基于"评估—优 化"迭代循环的技术债自动修复方法过程中面临的三项关键挑战,即告警信息难 详尽、意图测试易脱节和技术债依赖关系复杂。围绕上述挑战,本文对相关研究 工作进行系统梳理:首先综述技术债的识别告警方法,其次总结测试用例更新相 关研究进展,最后探讨技术债修复补丁的生成方法。

#### 2) 测试用例更新相关研究进展

现有的工作已经注意到既有测试用例和更新后的代码的脱节问题,他们将 代码差异作为输入更新测试用例。早期关于测试用例更新的研究主要依赖程序 分析技术与人工设计的启发式规则[18]。随着深度学习技术以及 LLM 的发展, 研究人员开始探索基于学习的测试用例更新方法。例如,Hu 等人采用基于 Transformer 的深度学习模型,对失效测试用例进行更新[19]。Chi 等人提出的 ReAccept 方法利用检索增强生成技术,从历史测试更新实例中检索少量示例, 并结合动态执行反馈,引导 LLM 迭代进行高质量的测试更新[20]。Liu 等人聚焦 于被测方法 API 发生变化的场景,利用语言服务器检索与测试更新相关的上下 文信息[21]。然而,这些方法关注的是更新后的代码和既有测试用例的脱节问题, 没有关注变更意图(文本)和既有测试用例脱节的问题,难以有效应对挑战 **2**。 (草稿)请于提交后重新下载PDF的正式稿

1994 年,Gamma 等人[23]提出并系统总结了软件设计模式,成为软件设计、 重构和手动修复技术债的指南。后续的研究人员针对特定类型的技术债开发了 一系列工具来自动化的进行重构[24]或确定重构顺序[25]。例如,Kohler 和 Salvaneschi[24]提出了一种将异步代码重构为响应式编程语言代码的自动化方法。 Gao 等人[26]关注自动修复测试异味。当需要同时解决多个测试异味时,他们根 据重构操作的类别确定修复优先级。然而,北京理工大学刘辉教授团队的研究指 出,还存在大量重构场景难以被现有的自动化方法覆盖[27]。自SATD提出以来,

研究人员以 SATD 为媒介,研究一般技术债的自动修复。具体而言,Zampetti 等 人[14]将技术债的修复方法划分为六类(如 API 替换、方法签名变更等),然后 设计深度学习模型分析 SATD 文本及相关代码,为不同变更提供修复方法的建 议,但他们的研究并未生成实际的补丁。近年来,Mastropaolo 等人[28]探索利用 预训练模型进行 SATD 的自动修复。但是,微调后的预训练模型 CodeT5[29]在 SATD 的自动修复任务上的成功率仅为 2%到 8%,而未经微调的预训练模型如 ChatGPT(GPT-3.5)在零样本环境下表现更差。Alhefdhi 等人[30]将 SATD 的自 动修复问题归类为神经机器翻译问题,利用程序自动修复问题的数据集进行训 练,然后在 SATD 修复数据集上进行验证,自动修复的成功率提升到了 14%。最 近,O'Brien 等人[31]研究利用基于 LLM 的自动代码补全工具(如 Copilot)修复 SATD。他们发现,虽然 Copilot 生成的代码有时能修复技术债,但也可能引入新 的技术债。然而,这些方法主要聚焦于单个技术债的修复或局部优化,而忽略了 不同技术债之间的依赖、耦合及传递关系,难以有效应对挑战 **3**。

值得一提的是,在这些方法的评估中,Mastropaolo 等人[28]和 Alhefdhi 等人 [30]通过比较生成补丁与基准数据集中真实补丁之间的文本相似度(如 BLEU、 CodeBLEU 等指标),评估补丁的合理性与接近程度。然而,这些方法未能评估 补丁是否破坏了原有的功能、是否存在技术债,难以评估补丁是否满足修复技术 债的目标。Kohler 和 Salvaneschi[24]通过已有测试用例评估技术债修复补丁的正 确性。当函数签名发生变化时,自动为该函数生成新的测试用例。然而,该方法 难以评估补丁是否引入了新的技术债,并且在签名发生变化的函数上难以保证 修改前后功能的一致性,难以评估补丁是否满足修复技术债的目标。尽管 Gao 等 人的方法评估了代码补丁中是否存在代码异味,但是他们并没有用评估结果引导 LLM 迭代优化代码补丁。与此同时,O'Brien 等人[31]则采用人工标注的方式, 对生成补丁的正确性进行手动评估。然而,该方法难以大规模的自动化应用,存 在较大的局限性。 (草稿)请于提交后重新下载PDF的正式稿

### 3. 发展动态分析

从国内外研究现状可以看出,尽管最近的方法探索了技术债的自动修复方 法,但是仅仅孤立的关注补丁的自动生成,没有评估补丁是否消除了技术债、是 否保持原有功能,更没有将评估结果用于迭代反馈引导 LLM 生成补丁。如果想 构建基于"评估—优化"迭代循环的技术债自动修复方法,针对现有关于技术债 的研究仍面临的三项关键挑战,即告警信息难详尽、意图测试易脱节和技术债依

![](_page_8_Picture_0.jpeg)

赖关系复杂,亟需围绕以下三个方面开展深入研究,破解相关核心挑战:

#### **1.**需要信息丰富、可操作的技术债告警信息自动生成方法

现有技术债告警方法多停留在"是否存在开发人员应该承认但没有承认的 技术债"的粗粒度判断层面[14,32],通常以二值分类结果作为输出,存在识别告 警解释不清晰、上下文信息不足的问题,缺乏可操作的修复线索,难以为后续基 于 LLM 生成补丁提供充分支撑。如果能够在识别是否存在技术债的基础上,能 够进一步生成信息丰富、可操作的技术债告警信息的自动化方法,就能够指导 LLM 生成更高质量的修复补丁。

#### **2.**需要面向技术债修复意图的测试用例自动更新方法

现有基于 LLM 的程序自动修复方法大多依赖既有测试用例对补丁进行评估, 没有考虑既有测试用例难以复用、需要更新的场景[12];现有的技术债修复方法 在评估阶段,也没有系统的评估补丁是否破坏了原有功能[24,28,30];尽管近年来 已有研究关注测试用例更新[33]、或提出基于文本更新代码的方法[22],但如何 利用技术债的描述来更新测试用例,仍缺乏系统性的研究,难以支撑对 LLM 生 成结果的可靠评估。如果能够提出面向技术债修复意图的测试用例自动更新方 法,给定需要修复的技术债,更新与之相关的测试用例,就能够评估候选补丁是 否破坏原有功能,提升利用 LLM 生成补丁的可靠性。 (草稿)请于提交后重新下载PDF的正式稿

#### **3.**需要考虑技术债依赖关系的补丁自动生成方法

现有的技术债补丁生成方法通常将技术债视为彼此独立的问题,聚焦于单 个技术债的修复,未能从整体视角系统分析不同技术债之间的依赖关系[34–36], 没有考虑技术债之间的修复顺序,缺乏对整体修复顺序的统筹规划,难以协助 LLM 高效的生成补丁。如果能够自动化的构建技术债的依赖关系、明确修复优 先级,并在此基础上生成补丁,就能够降低修复复杂度,避免修改范围频繁调整、 补丁多次返工与回滚,帮助 LLM 高效的修复技术债。

为了解决上述关键挑战,基于项目申请人在技术债识别识别、程序分析与智 能化软件工程领域积累的前期研究成果,本项目以开源软件系统中的 SATD 为 研究对象,以 LLM 为核心技术支撑,提出"基于评估引导迭代优化的软件技术 债自动修复研究"课题。项目围绕"基于动态上下文提取的信息丰富可操作的技 术债告警信息自动生成方法—基于技术债修复意图一致性验证的测试用例自动 更新方法—优先级制导、告警与测试更新协同驱动的技术债修复补丁生成方法" 的系统性研究思路,构建一套基于"评估—优化"迭代循环的自动修复方法与工

#### **1.**基于动态上下文提取的信息丰富可操作的技术债告警信息自动生成方法

针对现有技术债告警方法仅关注技术债是否存在、缺乏信息丰富且可操作 的告警信息、难以引导 LLM 有效生成补丁的问题,本项目将研究基于动态上下 文提取的信息丰富、可操作技术债告警信息自动生成方法。该研究内容的主要难 点在于,技术债与调用关系、数据依赖等多层次上下文高度相关,单纯依赖固定 范围的代码片段难以全面覆盖相关信息,容易导致缺失关键信息或引入噪声,从 而影响 LLM 对技术债的准确识别。为此,本项目重点探索技术债代码模式与动 态上下文协同驱动的技术债告警信息生成机制。首先,利用 LLM 对历史 SATD 样本、代码上下文及修复提交和外部知识库的联合分析,系统挖掘不同类型技术 债在结构特征、语义表现及修复行为等层面的模式。然后,根据待分析代码片段 中的信号,按需补充调用关系、数据依赖等上下文信息,直到能够形成对技术债 类别的初步假设。最后,根据候选技术债类型定向引导 LLM 按需获取相关上下 文信息,实现上下文信息的动态补充,从而生成包含类别、影响范围、修复意图 等要素的结构化技术债告警信息。 (草稿)请于提交后重新下载PDF的正式稿

#### **2.**基于技术债修复意图一致性验证的测试用例自动更新方法

针对既有测试用例没有随技术债修复过程同步演化、难以有效验证修复补 丁的功能、难以支撑对 LLM 生成结果的可靠评估的问题,本项目将研究基于技 术债修复意图一致性验证的测试用例自动更新方法。该研究内容的主要难点在 于技术债修复意图与测试用例之间缺乏显式映射关系。为此,本项目拟利用 LLM 的语义理解与推理能力,结合静态分析,开展相关测试用例的筛选与原有功能一 致性约束驱动下的自动更新。首先,结合原始 SATD 文本、代码上下文、技术债 模式及修复先验知识,推导并形式化表示技术债修复过程中允许的行为变化范 围,即结构化的修复意图。同时,结合静态分析与语义关联建模方法,在修复意 图的引导下筛选与当前修复任务相关的测试用例子集,并生成结构化的原始测 试意图。进一步地,在 LLM 与程序分析的协同下,将修复意图与原始测试意图 显式嵌入测试更新过程,并通过一致性验证与反馈优化机制更新测试用例。

#### 2. 研究目标

本项目以利用 LLM 构建基于"评估—优化"迭代循环的技术债自动修复方 法体系为总体目标,围绕补丁评估阶段技术债的告警、测试用例的更新与生成阶 段多技术债的协同修复这三个关键环节,推动技术债自动修复研究由"孤立的关 注单一补丁的自动生成"向"评估引导迭代优化"研究范式转变。具体而言,本 项目拟实现以下具体研究目标:

#### **1.**构建技术债告警信息对基于 **LLM** 自动修复的支撑能力

突破现有技术债告警方法仅停留在"是否存在"层面的局限,系统刻画技术 债的类型特征、语义内涵及其上下文依赖关系,自动生成包含修复意图等要素的 信息丰富、可操作告警信息,为引导 LLM 生成补丁提供丰富信息。

#### **2.**提高技术债修复补丁功能一致性的评估能力

针对技术债修复过程中测试用例与修复意图脱节、验证机制滞后的问题,构 建基于修复意图一致性约束驱动的测试用例自动更新方法,提升测试用例对补 丁功能正确性的自动评估能力,减少失效修复风险。

#### **3.**增强技术债修复顺序决策的整体性与合理性

改变将技术债视为相互独立问题的局部修复模式,系统建模不同技术债之 间的依赖关系与影响范围,结合开发任务背景与修复风险评估,推理合理的修复 顺序与协同修复策略,避免无序修改与重复返工,提升自动修复过程的整体效果。

#### 3. 拟解决的关键科学问题

![](_page_14_Picture_0.jpeg)

本项目各项研究内容的共同基础是信息充分、可操作的技术债告警信息。该 信息是 LLM 驱动的测试更新与补丁生成的关键。然而,现有技术债告警方法多 分析固定范围代码片段,难以理解技术债与调用关系、数据依赖之间的深层关系, 技术债告警结果停留在粗粒度判断层面,缺乏对技术债模式及修复线索的系统 刻画,难以指导 LLM 更新测试和生成补丁。从研究角度上看,该问题涉及理解 技术债在多层程序结构中的表现模式,而非简单的识别检测技术。由于不同的技 术债具有不同的代码模式,上下文的选择范围具有明显的不确定性,如何系统理 解技术债代码模式中的调用关系和数据依赖,并在技术债识别过程中基于已学 习模式动态引导 LLM 按需扩展上下文信息,生成信息充分、结构化且可操作的 技术债告警信息,是本项目必须首先回答的关键科学问题。

#### **2.**技术债修复意图一致性驱动的测试更新机制

本项目实现可信技术债自动修复的关键环节,在于构建与修复意图保持一 致的测试验证体系。只有当测试用例能够真实刻画技术债修复意图中允许与禁 止的行为,才能为 LLM 生成补丁提供可靠、有效的反馈信息。然而,既有测试 用例主要围绕原始功能需求设计,没有技术债修复所包含的优化与质量改进目 标;现有测试用例更新方法多以代码差异为输入,仅关注语法与接口变化下的适 配性调整,没有面向修复意图的验证。从研究角度上看,该问题涉及理解技术债 修复意图在测试语义中的表达,而非简单的软件测试。由于技术债修复意图与测 试语义之间缺乏显式映射关系,如何系统刻画技术债修复意图与既有测试的联 系,并在修复意图一致性驱动下更新测试用例,使测试行为能够与技术债修复目 标协同演进,是本项目亟需回答的关键科学问题。 (草稿)请于提交后重新下载PDF的正式稿

#### **3.**技术债依赖关系驱动的补丁生成机制

实现高质量的软件技术债自动修复,不仅依赖单个技术债的局部修复,更依 赖对多技术债协同修复过程的整体调控。由于技术债之间普遍存在复杂的结构 依赖,其修复过程具有显著的顺序约束与风险累积特征。若缺乏对技术债依赖关 系以及修复影响路径的系统建模,LLM 难以形成稳定、可控的修复决策过程。 从研究角度上看,该问题涉及理解技术债在软件中的依赖模式及其对修复行为 的影响,而非简单的软件修复。由于技术债之间的依赖关系往往隐含于调用关系、 数据依赖及模块耦合等多层次程序结构之中,如何系统刻画技术债依赖关系及 其修复影响路径,构建技术债依赖关系驱动的修复决策机制,并在此基础上驱动 LLM 生成修复补丁,是本项目拟解决的另一关键科学问题。

步骤二:基于修复意图的测试用例筛选与意图生成。该阶段以完整代码仓库 (包含测试代码)及步骤一生成的结构化修复意图为输入,通过静态分析与语义 理解,自动识别与目标技术债修复行为高度相关的测试用例集合,并生成面向测 试更新的原始测试意图的结构化表示。该步骤的难点在于,如何在缺乏显式代码 变更信息的前提下,将修复意图可靠的映射到具体测试用例上。为此,本项目结 合步骤一生成的结构化修复意图、调用关系分析结果、数据依赖分析结果,确定 与技术债修复相关的源代码,根据测试和生产代码映射关系,定位可能受修复影 响的候选测试集。进一步地,对候选测试进行语义分析,识别其所覆盖的功能路 径及异常触发场景,生成描述测试目标与验证重点的结构化原始测试意图。例如, 针对步骤一中识别出的"循环内频繁创建临时集合对象"性能类技术债,系统首 先基于静态调用分析定位该技术债所在方法、其被调用方法和这些方法相关的 测试代码。随后,进一步分析测试代码的语义信息,并据此生成对应的原始测试 意图的结构化表示:"该测试用例主要用于验证方法在不同输入规模下的输出内 容与顺序一致性。" (草稿)请于提交后重新下载PDF的正式稿

最后,本项目将以真实开源项目中的 SATD 文本及其对应的修复提交为基 础,构建包含 SATD 文本、修复前后代码和测试用例的数据集。在实验中,仅使 用修复前的代码和测试用例、SATD 文本作为输入,以验证方法的有效性,系统 评估本研究方法在测试可执行性、覆盖率等方面的性能。

# 3) 关于"优先级制导、告警与测试更新协同驱动的技术债修复补丁生成方法" 的研究方案

<span id="page-20-0"></span>图 5 展示了"优先级制导、告警与测试更新协同驱动的技术债修复补丁生成 方法"的研究方案。围绕技术债在自动修复过程中往往相互关联、修复顺序难以 合理确定的问题,本研究提出一套以技术债关系建模为核心的修复顺序推理方 案,构建从技术债修复依赖关系识别、修复顺序决策到技术债告警信息生成模块 与测试更新模块协同的技术债修复补丁生成的完整技术流程,分阶段开展如下 研究:

步骤一:技术债关联关系和修复依赖建模。该阶段以原始 SATD 文本、代码 文件及研究内容一中学习得到的技术债模式为输入,旨在识别每个技术债实例 的修复范围与潜在依赖。其主要难点在于,技术债之间的关联关系并不总是显式 体现为直接调用关系,而往往隐含于数据依赖、控制依赖及模块级耦合等多种程 序结构中,单一关系建模方式难以全面刻画其相互影响;同时,技术债之间的影 响具有传递性与累积性特征,局部修复可能沿依赖链条引发连锁修改,显著增加 修复成本甚至诱发新的技术债。针对上述问题,本研究结合轻量级静态分析与程 序结构分析方法,从调用、数据、控制及模块等多个维度识别技术债实例之间的 潜在关联,并将其统一建模为异构关系网络;进一步利用研究内容一中学习得到 的修复模式先验,结合 LLM 智能体与变更影响分析,从结构传播视角分析技术 债在关系网络中的影响传递路径与累积效应,识别可能引发大范围连锁修改的 关键节点,明确前置约束关系与修复范围,为后续修复顺序推理提供结构化基础。 例如,在某开源项目中同时存在三个 SATD 实例:一是"接口参数设计不统一" 的设计类技术债,二是"解析与校验逻辑重复实现"的冗余代码技术债,三是"循 环内频繁创建临时对象"的性能类技术债。表面上看三者分别位于不同方法中, (草稿)请于提交后重新下载PDF的正式稿

步骤二:技术债修复范围与优先级推理。该阶段以当前待执行的软件开发任 务(如新增功能实现、接口升级或性能优化需求)为输入,结合步骤一构建的技 术债关联关系网络,对相关 SATD 的修复范围与优先级进行系统推理。其主要难 点在于,不同开发任务对质量属性的关注重点存在显著差异,部分技术债在特定 任务背景下可能演化为关键约束因素,而某些技术债虽然与开发任务相关,但是 由于影响范围广泛可以继续推迟修复。为此,本研究首先分析开发任务涉及的功 能模块、接口变更范围及关键依赖路径,并将其映射至技术债关系网络中,识别 与当前任务强相关的技术债子图;进一步结合各技术债在该子图中的影响范围 等方面,对其潜在修复收益与风险进行综合评估。在此基础上,利用多目标排序 与约束推理等方法,自动生成与当前开发任务相匹配的 SATD 修复范围及优先 级序列,从而明确"哪些技术债必须优先处理、哪些可延后修复、哪些可暂时忽 略",为后续补丁生成提供决策依据。例如,在当前开发任务为"为现有系统新 增批量数据导出功能"的场景下,系统将该任务涉及的代码区域映射至技术债关 联网络后,识别出步骤一提及的三个需要修复的 SATD 实例。进一步分析发现, "接口参数设计不统一"涉及多个核心接口及其上下游模块,处于多个调用链的 上游位置,影响范围最广,修复成本较高。相比之下,冗余解析逻辑与循环内对 象分配问题的影响范围较为局部,依赖层级较浅,传播风险处于中低水平。因此 优先修复冗余解析逻辑与循环内对象分配问题。 (草稿)请于提交后重新下载PDF的正式稿

步骤三:多模块协同的技术债修复补丁生成。该阶段以排序后的技术债修复 优先级为输入,在研究内容一中的技术债告警信息生成方法模块以及研究内容 二测试用例的自动化更新方法模块的多源反馈协同机制驱动下,执行高可信的 技术债修复补丁自动生成与优化。具体而言,本研究基于 LLM 构建多约束补丁 生成框架,将修复优先级信息、修复意图及技术债修复模式知识统一嵌入生成提 示模板中,引导模型按照既定顺序逐项生成修复补丁。生成过程中,系统同步调 用技术债告警信息生成模块与测试用例的自动化更新模块,对候选补丁进行功 能一致性验证与技术债消除效果评估。对于未通过验证的补丁,系统将自动分析

#### 5. 本项目的特色与创新点

本项目面向软件技术债自动修复这一关键任务,提出基于"评估—优化"迭 代反馈的技术债自动修复研究思路。与现有方法侧重单一阶段优化不同,本项目 从修复全过程视角出发,系统研究技术债告警信息生成、测试用例更新与多技术 债协同修复等关键问题,通过评估结果持续引导修复策略优化,形成评估引导的 自动修复闭环机制。该研究思路不仅能够提升技术债自动修复的准确性与可靠 性,还为大语言模型在软件维护中的可信应用提供新的方法框架,推动技术债自 动修复研究由"孤立的关注单一补丁的自动生成"向"评估引导迭代优化"研究 范式转变。 (草稿)请于提交后重新下载PDF的正式稿

在此基础上,本项目的主要创新点体现在以下几个方面:

## **1.**首次提出面向自动修复的信息丰富、可操作技术债告警信息生成方法

突破现有研究主要停留在告警"是否存在 SATD"层面的局限,从自动修复出 发将技术债的类型、语义含义、代码上下文及可能的修复路径统一纳入告警信息 描述框架。该方法通过小样本学习技术债代码模式并结合动态上下文推理技术 债语义,使技术债由低信息量告警信号转化为具有明确修复语义的结构化对象, 为技术债自动修复、测试更新与修复决策提供语义基础,推动技术债识别研究从 "检测问题"向"修复驱动的告警信息生成"的研究范式转变。

#### **2.**首次引入修复意图驱动的技术债测试更新机制

突破现有测试更新方法主要依赖代码差异进行适配性调整的局限,将技术 债修复意图显式引入测试更新过程,构建面向技术债自动修复的测试更新框架。 该机制通过解析技术债修复意图并建立其与既有测试语义之间的关联关系,在 无需代码差异输入的情况下自动更新测试用例,使测试验证从"是否通过既有测

## **3.**首次构建技术债依赖关系驱动的自动修复顺序建模机制

突破现有技术债修复方法通常将多个技术债视为彼此独立问题进行处理的 局限,将技术债之间的依赖关系显式引入修复决策过程,构建面向协同治理的技 术债关系建模框架。该机制通过系统刻画技术债之间的依赖、耦合等关系,对不 同技术债的修复影响范围与潜在风险进行联合分析,从而自动推理合理的修复 顺序,使修复过程从依赖开发经验的局部决策转变为可推理的自动化过程,有效 避免局部修复引发的重复修改问题,推动技术债自动修复研究从"单点修复问题" 向"协同治理问题"转变。 <sup>图</sup> <sup>6</sup> 本项目年度研究计划 (草稿)请于提交后重新[下](#page-23-0)载PDF的正式稿

#### 2) 可行性分析

#### 研究思路可行性

本项目围绕技术债自动修复过程中告警信息难详尽、意图测试易脱节和技 术债依赖关系复杂等关键挑战,构建了基于动态上下文提取的信息丰富可操作 的技术债告警信息自动生成方法、基于技术债修复意图一致性验证的测试用例 自动更新方法和优先级制导、告警与测试更新协同驱动的技术债修复补丁生成 方法为核心的整体研究思路,并通过递进式与协同式相结合的方式逐步推进。从 整体结构来看,本项目依次解决技术债告警信息的表达、测试更新与修复顺序推 理及补丁生成等关键环节问题,避免了单点修复难以稳定落地的风险。基于动态 上下文提取的信息丰富可操作的技术债告警信息自动生成方法为修复过程提供 信息丰富、可操作的指导,基于技术债修复意图一致性验证的测试用例自动更新 方法为补丁评估提供语义约束与反馈支撑,基于技术债修复意图一致性验证的 测试用例自动更新方法则保障多技术债场景下修复顺序的合理性与整体稳定性。 各阶段之间通过中间成果复用与反馈优化形成闭环体系,确保自动修复过程在 复杂软件系统中的系统性。 (草稿)请于提交后重新下载PDF的正式稿

#### 研究风险及其应对措施

(1)技术债类型覆盖不足的风险。单一开源项目中的技术债类型与表现形 式相对有限,难以全面覆盖不同类别的技术债,从而可能影响技术债模式学习与 方法评估的代表性。为此,本项目拟从多个开源项目中收集尽可能多的项目,构 建跨项目的数据集,以提升技术债类型的覆盖范围,并通过多项目实验验证方法

![](_page_31_Picture_0.jpeg)

的泛化能力。
